# 2장. 방법론

2장에서 다루는 내용은 다음과 같다:
- 핵심 성능 지표인 지연시간, 사용률, 포화도를 이해하기
- 측정된 시간을 스케일해서 나노초 수준까지 감각적으로 이해하기
- 튜닝 과정에서 생기는 트레이드오프와 분석을 어디까지 진행할지 판단하는 기준 이해하기
- 부하 문제와 아키텍처 문제를 구별하기
- 자원 분석과 워크로드 분석의 관점을 이해하기
- USE 방법론, 워크로드 특성화, 지연시간 분석, 정적 성능 튜닝, 성능 사례 연구 등 여러 성능 분석 방법론 익히기
- 통계와 큐 이론의 기초 개념 이해하기

<br>

## 2.1 용어

- IOPS(Input/output operations per second): 초당 처리되는 입출력 연산 횟수를 의미한다. 디스크에서는 보통 초당 읽기/쓰기 요청 수를 뜻하며, 저장장치의 작업량을 볼 때 자주 사용하는 지표이다.
- 스루풋(throughput): 단위 시간당 처리량을 의미한다. 네트워크에서는 초당 전송 바이트 수나 비트 수를 뜻하는 경우가 많고, 데이터베이스 같은 환경에서는 초당 트랜잭션 수처럼 작업 처리량을 뜻하기도 한다.
- 응답 시간(response time): 요청이 완료될 때까지 걸리는 전체 시간이다. 대기 시간뿐 아니라 실제 처리 시간과 결과를 돌려주는 시간까지 포함한 값이다.
- 지연시간(latency): 보통 요청이 처리되기까지 기다리는 시간을 뜻한다. 다만 문맥에 따라 전체 연산 시간을 의미하기도 해서, 응답 시간과 같은 뜻으로 쓰이는 경우도 있음을 주의해야 한다.
- 사용률(utilization): 어떤 자원이 일정 시간 동안 얼마나 바쁘게 일했는지를 나타내는 기준이다. CPU처럼 작업 시간 비율로 표현할 수도 있고, 메모리처럼 전체 용량 중 사용 중인 비율을 뜻하기도 한다.
- 포화도(saturation): 자원이 당장 처리하지 못하고 큐에 쌓아 둔 작업의 정도를 의미한다. 자원이 감당할 수 있는 수준을 넘어서기 시작했는지를 판단할 때 중요하다.
- 병목 지점(bottleneck): 전체 시스템 성능을 제한하는 자원을 뜻한다. 성능 개선은 결국 이 병목 지점을 찾아 제거하거나 완화하는 과정이라고 볼 수 있다.
- 워크로드(workload): 시스템에 실제로 가해지는 부하를 의미한다. 데이터베이스에서는 클라이언트가 보내는 쿼리와 명령들의 집합이 워크로드가 된다.
- 캐시(cache): 더 느린 저장장치에 직접 접근하지 않고도 데이터를 빠르게 처리하기 위해 사용하는 작은 저장 공간이다. 자주 쓰는 데이터를 미리 복사하거나 버퍼링해서 전체 성능을 높이는 역할을 한다.

<br>

## 2.2 모델

### 2.2.1 테스트 중인 시스템

테스트 중인 시스템(SUT, System Under Test)은 성능 분석의 대상이 되는 시스템을 의미한다.<br>
이 시스템의 성능을 볼 때는 입력과 출력만 보는 것이 아니라, 그 사이에 영향을 미치는 여러 교란(perturbation) 요인도 함께 고려해야 한다.<br>
예를 들어 예약된 시스템 작업, 같은 시스템을 사용하는 다른 사용자, 동시에 실행 중인 다른 워크로드가 모두 성능에 영향을 줄 수 있다.

<br>

특히 클라우드 환경에서는 이런 교란 요인을 파악하기가 더 어렵다.<br>
게스트 시스템 내부에서는 같은 물리적 호스트에서 실행 중인 다른 테넌트의 활동을 직접 볼 수 없는 경우가 많기 때문이다.<br>
즉, 현재 보이는 성능 문제의 원인이 내부 애플리케이션이 아니라 외부 간섭일 수도 있으므로, 시스템을 주의 깊게 분석해야 한다.

<br>

또한 현대 시스템은 하나의 서버만으로 구성되지 않고, 로드 밸런서, 프락시 서버, 웹 서버, 캐시 서버, 애플리케이션 서버, 데이터베이스 서버, 스토리지 시스템 등 여러 구성 요소가 함께 입력 워크로드를 처리한다.<br>
이처럼 복잡한 환경에서는 각 구성 요소를 먼저 단순하게라도 나열하고 연결 관계를 파악하는 것만으로도, 이전에 간과했던 교란 요소나 병목 후보를 찾는 데 도움이 된다.

<br>

### 2.2.2 큐 시스템

일부 시스템 구성 요소나 자원은 큐 시스템(queueing system)으로 모델링할 수 있다.<br>
큐 시스템이란 요청이 도착했을 때 바로 처리되지 못한 작업이 줄을 서서 대기하고, 자원이 이를 순차적으로 처리하는 구조를 말한다.

<br>

디스크는 대표적으로 큐 시스템으로 설명하기 좋은 자원이다.<br>
요청 수가 많아질수록 대기열이 길어지고, 그에 따라 응답 시간도 나빠질 수 있다.<br>
이런 모델을 이용하면 특정 자원에 부하가 증가했을 때 성능이 어떤 식으로 저하되는지 예측할 수 있다.

<br>

## 2.3 개념

### 2.3.1 지연시간

지연시간(latency)은 어떤 연산이 실제로 수행되기 전에 기다려야 하는 시간을 의미한다.<br>
예를 들어 HTTP 요청에서는 네트워크 연결이 먼저 수립되어야 데이터 전송이 가능하므로, 연결이 완료될 때까지 기다리는 시간이 지연시간이 된다.<br>
이 지연시간과 실제 연산 시간이 합쳐진 값이 응답 시간(response time)이다.

<br>

지연시간은 측정 위치에 따라 다르게 보일 수 있다.<br>
웹 페이지를 불러오는 시간도 DNS 지연시간, TCP 연결 지연시간, 데이터 전송 시간, 브라우저 렌더링 시간 등으로 나누어 볼 수 있다.<br>
그래서 지연시간을 다룰 때는 단순히 느리다라고 말하기보다, 어떤 구간의 지연시간인지 함께 구분하는 것이 중요하다.<br>
또한 지연시간은 시간 단위로 표현되기 때문에 여러 성능 문제를 같은 기준으로 비교하고, 개선 효과를 추정하는 데 유리하다.<br>
반대로 IOPS처럼 시간 단위가 아닌 다른 지표만으로는 성능 차이를 직관적으로 비교하기 어려울 수 있다.

<br>

### 2.3.2 시간 스케일

시스템의 여러 구성 요소는 서로 매우 다른 시간 스케일로 동작한다.<br>
CPU 레지스터나 캐시 접근은 나노초 단위로 이뤄지지만, 메모리 접근은 그보다 느리고, SSD나 디스크 I/O, 네트워크 왕복 시간은 훨씬 더 큰 단위의 지연을 가진다.
성능 분석에서는 각 연산이 어느 정도의 시간 스케일에 속하는지 먼저 감을 잡아야 한다. 그래야 어떤 지연이 정상 범위인지, 어떤 지연이 비정상적으로 큰 문제인지 판단하기 쉬워진다.

<br>

### 2.3.3 트레이드오프

성능 튜닝에는 항상 트레이드오프가 따른다.좋음, 빠름, 저렴함 중 두 가지만 동시에 만족하기 쉽다.<br>
대표적인 예로 CPU와 메모리 사이의 트레이드오프가 있다. 메모리를 더 써서 캐시를 늘리면 CPU 작업을 줄일 수 있고, 반대로 CPU를 더 사용해서 압축을 수행하면 메모리 사용량을 줄일 수도 있다.<br>
튜닝 파라미터도 서로 상충하는 경우가 많다.<br>
예를 들어 파일 시스템 레코드 크기를 작게 하면 임의 접근에는 유리하지만 연속 전송에는 불리할 수 있고, 네트워크 버퍼를 줄이면 연결당 메모리 사용량은 줄지만 스루풋은 떨어질 수 있다.<br>
따라서 시스템을 바꿀 때는 단일 지표만 보지 말고, 무엇을 얻고 무엇을 포기하는지 함께 판단해야 한다.

<br>

### 2.3.4 튜닝을 위한 노력

성능 튜닝은 가능하면 작업이 실제로 발생하는 가장 가까운 지점에서 수행하는 것이 가장 효과적이다.<br>
애플리케이션이 불필요한 쿼리나 연산을 만들어내고 있다면, 가장 큰 효과는 운영 체제나 저장 장치가 아니라 애플리케이션 자체를 고치는 데서 나온다.<br>
예를 들어 애플리케이션 수준에서는 불필요한 데이터베이스 쿼리를 제거해 큰 폭의 성능 개선을 얻을 수 있지만, 저장 장치 수준까지 내려가면 이미 상위 계층 비용이 발생한 뒤라 개선 폭이 상대적으로 작을 수 있다.<br>
즉, 같은 노력이라도 어디를 튜닝하느냐에 따라 얻는 효과가 크게 달라질 수 있다.<br>
다만 관찰의 출발점을 무조건 애플리케이션에 둘 필요는 없다.<br>
느린 쿼리나 CPU 사용 증가는 운영 체제 도구를 통해 더 쉽게 드러날 수 있고, 특히 클라우드 환경처럼 애플리케이션이 자주 바뀌는 곳에서는 운영 체제 수준 분석이 오히려 더 유용할 수 있다.

<br>

### 2.3.5 적합성의 수준

성능 분석의 깊이와 수준은 조직이나 환경에 따라 달라진다.<br>
어떤 조직은 커널 내부, CPU 성능 카운터, 트레이싱 도구까지 깊게 들어가 분석하는 반면, 어떤 조직은 기초적인 모니터링과 알림만으로도 충분하다고 판단할 수 있다.<br>
이는 투자 대비 효과(ROI)가 다른 것이다. 대규모 데이터센터나 클라우드 기업은 성능 개선이 곧 큰 비용 절감으로 이어지기 때문에 깊은 분석이 정당화되지만, 소규모 조직은 상대적으로 가벼운 수준의 분석을 선택할 수 있다 <br>
또한 성능 투자의 가치는 비용 절감뿐 아니라 사용자 경험 개선에도 있다.<br>
아주 극단적인 사례로는 금융 거래나 초단타매매처럼 지연시간 자체가 경쟁력이 되는 환경이 있으며, 이런 환경에서는 막대한 비용도 정당화될 수 있다.

<br>

### 2.3.6 분석을 언제 중단할 것인가

성능 분석에서 어려운 문제 중 하나는 언제 멈출지를 정하는 일이다. 도구도 많고 더 파볼 수 있는 부분도 많기 때문에, 끝없이 분석하다 보면 오히려 시간과 비용을 과도하게 쓰게 될 수 있다. <br>
분석을 멈출 수 있는 기준는 다음이 있다:
- 성능 문제의 주요 원인을 충분히 설명할 수 있을 때
- 추가 분석으로 얻을 이익보다 분석 비용이 더 클 때
- 더 큰 효과가 기대되는 다른 문제가 우선순위일 때

<br>

### 2.3.7 성능 개선의 한시성

성능 개선 결과와 튜닝 권장 사항은 영구적이지 않을 수 있다.<br>
사용자 수가 늘어나거나, 하드웨어가 바뀌거나, 소프트웨어와 펌웨어가 업데이트되면 과거에 유효했던 튜닝 값이 더 이상 맞지 않을 수 있다. <br>
그래서 튜닝 파라미터를 바꿀 때는 왜 바꿨는지와 어떤 환경에서 유효했는지를 기록으로 남기는 것이 중요하다.<br>
버전 관리 시스템이나 설정 관리 도구를 이용해 변경 이력을 남기면, 나중에 해당 설정의 맥락을 다시 확인하기 쉬워진다.

<br>

### 2.3.8 부하 vs. 아키텍처

애플리케이션 성능 저하는 단순히 부하가 많아서일 수도 있고, 시스템 아키텍처 자체가 비효율적이어서일 수도 있다. 이 둘을 구분하는 것은 성능 분석에서 매우 중요하다. <br>
예를 들어 단일 스레드 애플리케이션이 한 CPU만 바쁘게 쓰고 나머지 CPU는 놀고 있는데 요청이 큐에 쌓인다면, 이는 과부하라기보다 아키텍처 문제에 가깝다.<br>
반대로 멀티스레드 애플리케이션에서 모든 CPU가 이미 최대한 활용되고 있고 그럼에도 요청이 계속 쌓인다면, 이는 자원 자체가 부족한 부하 문제에 가깝다.<br>
즉, 큐가 길다고 해서 무조건 자원이 부족한 것은 아니다.<br>
큐가 왜 생겼는지, 병렬 처리 구조가 적절한지, 락 경쟁 같은 설계 문제가 없는지를 함께 봐야 한다.

<br>

### 2.3.9 규모 확장성

규모 확장성(scalability)은 시스템에 가해지는 부하가 증가할 때 성능이 어떻게 변하는지를 의미한다.<br>
이상적인 경우 스루풋은 부하 증가에 비례해 선형적으로 증가하지만, 실제 시스템은 어느 지점부터 자원 경쟁과 간섭이 생기면서 선형성을 잃게 된다.<br>
이 경계 지점을 무릎점(knee point)이라고 하며, 이후에는 응답 시간이 빠르게 나빠지거나 스루풋 증가가 둔화된다.<br>
더 나아가 자원이 포화되면 컨텍스트 스위치나 경합 오버헤드 때문에 오히려 전체 스루풋이 감소할 수도 있다.

<br>

응답 시간 관점에서도 비슷한 현상이 나타난다.<br>
메모리 부족으로 페이지 교체가 발생하거나 디스크 I/O가 대기열에 쌓이면 성능이 급격히 무너질 수 있다.<br>
그래서 선형 확장성을 유지하려면 무한히 큐를 늘리기보다, 자원이 부족할 때는 요청을 거절하거나 실패를 빠르게 반환하는 설계가 더 나을 수 있다.

<br>

### 2.3.10 지표

성능 지표(performance metrics)는 시스템, 애플리케이션, 또는 추가 도구가 제공하는 여러 통계 중에서 분석과 모니터링 대상으로 선택한 값들이다.<br>
대표적인 지표로는 스루풋, IOPS, 사용률, 지연시간 등이 있다.

<br>

다만 같은 지표라도 문맥에 따라 의미가 달라질 수 있다.<br>
예를 들어 데이터베이스 스루풋은 초당 쿼리 수일 수 있고, 네트워크 스루풋은 초당 비트 수나 바이트 수일 수 있다.<br>
따라서 지표를 볼 때는 이름만이 아니라 무엇을 어떤 단위로 세고 있는지 함께 확인해야 한다.

<br>

또한 지표 수집 자체에도 오버헤드가 있다.<br>
지표를 모으고 저장하는 과정이 CPU를 쓰고 시스템에 영향을 줄 수 있는데, 이를 관찰자 효과라고 한다.<br>
게다가 지표는 복잡하거나 부정확할 수 있고, 버그 때문에 잘못된 값을 보여줄 수도 있으므로 무조건 신뢰해서는 안 된다.

<br>

### 2.3.11 사용률

사용률(utilization)은 자원이 얼마나 바쁘게 일하고 있는지를 나타내는 지표이지만, 실제로는 두 가지 방식으로 이해할 수 있다.<br>
하나는 시간 기반 사용률이고, 다른 하나는 수용량 기반 사용률이다.

<br>

시간 기반 사용률은 전체 관찰 시간 중 자원이 실제로 바쁘게 동작한 시간의 비율이다.<br>
책에서는 이를 `U = B / T`로 설명한다. 여기서 `B`는 자원이 바빴던 시간, `T`는 전체 관찰 시간이다.<br>
운영 체제 도구가 흔히 보여주는 사용률은 대체로 이 의미에 가깝다.

<br>

하지만 시간 기준으로 100% 바쁘다고 해서, 반드시 더 이상 아무 일도 못 한다는 뜻은 아니다.<br>
예를 들어 엘리베이터가 계속 움직이고 있어도 더 많은 사람을 태울 여지가 있을 수 있는 것처럼, 어떤 자원은 100% 바쁜 상태에서도 추가 작업을 받아들일 수 있다.

<br>

수용량 기반 사용률은 현재 성능이 그 자원의 최대 처리 능력 중 얼마를 쓰고 있는지를 보는 개념이다.<br>
이 기준에서는 100%에 도달하면 진짜로 더 이상 여유가 없는 상태다.<br>
이상적으로는 두 관점을 함께 봐야 하지만, 실제로는 수용량 자체를 정확히 알기 어려운 경우가 많다고 설명한다.

<br>

### 2.3.12 포화도

포화도(saturation)는 자원이 처리할 수 있는 양보다 더 많은 작업이 들어와 대기열이 생기는 상태를 의미한다.<br>
수용량 기준으로는 사용률이 100%를 넘는 시점부터 포화가 시작되며, 이후 추가 작업은 큐에 쌓인다.

<br>

포화도가 생기면 작업은 큐에서 기다리는 동안 지연을 겪게 되고, 그 자체가 성능 문제로 이어진다.<br>
그래서 단순히 "바쁘다"는 것보다 "얼마나 밀려 있는가"를 보여주는 포화도는 성능 병목을 이해하는 데 매우 중요한 개념이다.

<br>

또한 시간 기반 사용률 관점에서는 자원이 한 번에 처리할 수 있는 병렬성의 정도에 따라 100% 사용률 이전에도 큐잉이 나타날 수 있다.<br>
즉, 포화는 단순히 숫자 100% 하나로만 판단할 수 있는 문제가 아니다.

<br>

### 2.3.13 프로파일링

프로파일링(profiling)은 대상 시스템의 상태를 기록해 나중에 검토하고 이해할 수 있도록 하는 작업이다.<br>
성능 분야에서는 보통 일정 간격으로 시스템 상태를 샘플링한 뒤, 그 샘플들을 분석하는 형태로 수행된다.

<br>

스루풋이나 사용률 같은 단일 지표가 전체 크기를 보여준다면, 프로파일링은 시스템 내부에서 어디에 시간이 쓰이고 있는지 더 입체적으로 보여준다.<br>
샘플링 간격이 짧을수록 더 자세한 관찰이 가능하지만, 그만큼 비용도 커질 수 있다.

<br>

예를 들어 CPU 명령어 포인터나 스택 트레이스를 샘플링하면 어떤 코드 경로가 CPU 자원을 많이 쓰는지 파악할 수 있다.<br>
즉, 프로파일링은 "얼마나 바쁜가"를 넘어서 "어디에서 바쁜가"를 찾는 도구라고 볼 수 있다.

<br>

### 2.3.14 캐싱

캐싱(caching)은 느린 저장 장치에서 가져온 결과를 더 빠른 저장 장치에 저장해, 이후 접근 시간을 줄이는 대표적인 성능 향상 기법이다.<br>
예를 들어 디스크 블록을 메인 메모리에 올려두거나, CPU가 메모리 접근을 줄이기 위해 여러 단계의 하드웨어 캐시를 사용하는 것이 모두 캐싱의 예이다.

<br>

캐시를 이해할 때 중요한 지표 중 하나는 히트율(hit rate)이다.<br>
히트율은 전체 접근 중 필요한 데이터를 캐시에서 바로 찾은 비율을 의미하며, 히트율이 높을수록 빠른 계층에서 작업이 더 많이 처리된다는 뜻이다.<br>
다만 히트율만 보면 충분하지 않고, 시간당 미스 횟수처럼 실제 비용에 더 가까운 지표도 함께 봐야 한다고 설명한다.

<br>

예를 들어 히트율이 더 높아 보여도 미스 횟수가 훨씬 많다면, 실제 디스크 접근 비용은 더 커질 수 있다.<br>
그래서 캐시 성능은 히트율만으로 단순 비교하기보다, 히트와 미스의 지연시간을 함께 고려해 전체 실행 시간 관점에서 판단해야 한다.

<br>

또한 캐시 정책도 중요하다.<br>
MRU, LRU, MFU, LFU 같은 정책은 제한된 공간에 어떤 데이터를 유지하고 어떤 데이터를 내보낼지를 결정한다.<br>
캐시는 차가운 상태에서 시작해 시간이 지나며 따뜻해지고, 자주 요청되는 데이터가 충분히 쌓이면 뜨거운 상태가 된다. 캐시가 커지거나 다음 계층 저장장치가 느릴수록 이 warming 과정은 더 오래 걸릴 수 있다.

<br>

### 2.3.15 모른다는 것을 아는 것들

저자는 성능 분석에서 "이미 알고 있는 것", "모른다는 것을 아는 것", "모른다는 것조차 모르는 것"을 구분하는 태도가 중요하다고 말한다.<br>
이 구분은 단순한 개념 설명이 아니라, 실제로 어디까지 분석할 수 있는지를 결정하는 사고방식과 연결된다.

<br>

이미 알고 있는 것은 예를 들어 CPU 사용률을 봐야 한다는 사실과 현재 값이 얼마인지 알고 있는 상태이다.<br>
모른다는 것을 아는 것은, 예를 들어 CPU가 바쁜 원인을 찾기 위해 프로파일링을 할 수 있다는 사실은 알지만 아직 확인하지 않은 상태이다.<br>
반면 모른다는 것조차 모르는 것은, 어떤 서브시스템이나 원인 자체를 떠올리지 못해 아예 조사 대상에 올리지 못하는 상태를 의미한다.

<br>

시스템을 더 깊게 이해할수록 "모른다는 것을 모르는 것"이 줄어들고, 그것들이 "모른다는 것을 아는 것"으로 바뀐다고 설명한다.<br>
즉, 성능 분석 역량이란 단순히 답을 많이 아는 것이 아니라, 아직 보지 않은 원인과 질문의 존재를 더 많이 인식할 수 있게 되는 과정이라고 볼 수 있다.

<br>

## 2.4 관점

성능 분석은 하나의 방식으로만 이뤄지는 것이 아니라, 무엇을 중심에 두고 보느냐에 따라 전혀 다른 분석 흐름이 만들어진다고 설명한다.
이 두 관점은 워크로드 분석(workload analysis)과 자원 분석(resource analysis)이다.<br>
워크로드 분석은 애플리케이션과 요청의 흐름을 위에서 아래로 따라가는 하향식 관점에 가깝고, 자원 분석은 CPU, 메모리, 디스크, 네트워크 같은 시스템 자원부터 아래에서 위로 살펴보는 상향식 관점에 가깝다.<br>

<br>

### 2.4.1 자원 분석

자원 분석은 시스템 자원부터 먼저 살펴보는 방식이다.<br>
대상은 CPU, 메모리, 디스크, 네트워크 인터페이스, 버스, 인터커넥트 같은 물리적 또는 시스템 수준 자원이며, 주로 시스템 관리자가 많이 사용하는 관점이다.<br>
자원 분석의 목적은 크게 두 가지이다.<br>
하나는 특정 자원이 실제 성능 문제를 일으키고 있는지 확인하는 것이고, 다른 하나는 새로운 시스템을 설계하거나 기존 시스템의 자원이 언제 고갈될지를 예측하는 수용량 계획이다.

<br>

이 관점은 기본적으로 사용률을 중심에 두고 본다.<br>
어떤 자원이 언제 한계에 도달하는지, 이미 포화 상태에 가까운지, 현재 부하를 얼마나 감당하고 있는지를 파악하는 데 초점이 있다.<br>
CPU처럼 사용률 지표가 명확한 자원도 있지만, 네트워크처럼 현재 스루풋을 최대 대역폭과 비교해 사용률을 추정해야 하는 자원도 있다.

<br>

자원 분석에서 자주 사용하는 지표는 IOPS, 스루풋, 사용률, 포화도이다.<br>
또한 지연시간도 특정 자원이 현재 부하에 얼마나 잘 대응하고 있는지를 판단하는 데 유용하게 쓰일 수 있다.

<br>

저자는 자원 분석이 매우 흔한 접근 방식이지만, 이것만이 유일한 관점은 아니라고 강조한다.<br>
`vmstat`, `iostat`, `mpstat` 같은 운영 체제 도구는 자원 분석에 매우 유용하지만, 성능 문제를 항상 이 관점만으로 설명할 수 있는 것은 아니다.

<br>

### 2.4.2 워크로드 분석

워크로드 분석은 애플리케이션에 가해지는 부하와 그에 대한 응답, 즉 애플리케이션의 성능을 중심으로 살펴보는 방식이다.<br>
이 관점은 주로 애플리케이션 개발자나 지원 부서에서 많이 사용하며, 요청이 어떻게 들어오고 어떤 결과를 내는지를 분석의 출발점으로 삼는다.

<br>

워크로드 분석에서 중요하게 보는 것은 요청 자체의 특성과 응답 시간, 그리고 완료 결과이다.<br>
요청의 특성을 요약하고 분류하는 과정을 워크로드 특성화(workload characterization)라고 설명하는데, 데이터베이스라면 클라이언트 호스트, 데이터베이스 이름, 테이블, 쿼리 문자열 같은 정보가 여기에 해당한다.<br>
이 과정을 통해 불필요하거나 불균형한 요청을 찾아낼 수 있고, 빠르긴 하지만 아예 없어도 되는 작업을 줄이는 방향으로도 성능 개선이 가능하다.

<br>

이 관점에서 가장 중요한 지표는 지연시간이다.<br>
예를 들어 MySQL에서는 쿼리 지연시간, 웹 서버에서는 HTTP 요청 지연시간이 핵심 지표가 된다.<br>
여기서의 지연시간은 사실상 애플리케이션 응답 시간과 같은 의미로 쓰인다.

<br>

워크로드 분석은 문제가 보이면 그 원인을 더 아래 계층으로 파고 들어가는 방식으로 이어진다.<br>
즉, 애플리케이션에서 시작해 라이브러리, 운영 체제, 커널 수준까지 드릴다운하면서 지연시간의 원인을 추적하게 된다.<br>
또한 요청이 빠르게 끝났더라도 오류로 인해 조기 종료된 것이라면 재시도가 발생해 전체 지연시간이 더 나빠질 수 있으므로, 완료 결과까지 함께 봐야 한다.

<br>

워크로드 분석에 적합한 주요 지표는 스루풋과 지연시간이다.<br>
이들은 요청이 얼마나 많이 처리되고 있는지, 그리고 사용자가 체감하는 응답 성능이 어떤지를 직접적으로 보여주는 지표이다.

<br>

## 2.5 방법론

### 2.5.1 가로등 반방법론

가로등 반방법론은 체계적인 방법 없이, 익숙한 도구나 눈에 잘 보이는 현상만 들여다보는 방식이다.<br>
문제를 잃어버린 위치가 아니라 가장 밝은 곳에서 찾는다는 "가로등 효과"에 빗댄 표현으로, 분석자가 잘 아는 도구만 반복해서 보는 상황을 뜻한다.<br>
예를 들어 특별한 이유 없이 `top` 화면만 계속 들여다보거나, 인터넷에서 본 튜닝 파라미터를 일단 적용해 보는 식이 여기에 해당한다.<br>
이 방식은 우연히 문제를 찾을 수도 있지만, 더 중요한 원인을 놓치기 쉽고 오탐지에 시간을 낭비할 가능성이 크다.

<br>

### 2.5.2 임의 변경 반방법론

임의 변경 반방법론은 문제가 사라질 때까지 설정이나 파라미터를 무작위로 바꿔보는 방식이다.<br>
무언가를 바꾸고 성능을 측정하고, 반대로도 바꿔보고, 조금이라도 좋아 보이면 채택하는 식으로 반복한다.<br>
이 방식은 운 좋게 테스트 부하에서 효과를 보는 튜닝 값을 찾을 수는 있지만, 시간이 오래 걸리고 왜 좋아졌는지 설명하기 어렵다.<br>
더구나 그 설정이 특정 버그를 우회한 임시 해법이었다면, 나중에 환경이 바뀌었을 때 오히려 문제를 더 키울 수도 있다.

<br>

### 2.5.3 다른 사람 비난 반방법론

다른 사람 비난 반방법론은 자신이 책임지지 않는 구성 요소를 먼저 의심하고, 그 문제라고 가정한 뒤 다른 팀으로 넘기는 방식이다.<br>
예를 들어 충분한 근거 없이 네트워크 문제일 것 같다며 네트워크 팀에 넘기는 식이다.<br>
이 방법의 문제는 실제 분석 없이 가정부터 세운다는 점이다.<br>
근거가 약하면 다른 팀의 시간을 낭비하게 되고, 진짜 원인을 찾는 시점도 늦어진다.<br>
이런 상황을 피하려면 어떤 도구로 어떤 근거를 확인했는지 먼저 요구해야 한다.

<br>

### 2.5.4 전용 체크리스트 방법론

전용 체크리스트 방법론은 특정 환경에서 자주 겪는 문제를 미리 목록으로 정리해 두고, 그 순서대로 검사하는 방식이다.<br>
지원 인력이 짧은 시간 안에 서버나 애플리케이션을 점검할 때 특히 자주 쓰인다.<br>
이 방법은 최근 경험과 반복되는 문제를 빠르게 점검할 수 있다는 장점이 있다.<br>
하지만 특정 시점과 환경에 맞춰진 권장 사항에 가깝기 때문에, 시스템이 바뀌면 체크리스트도 계속 업데이트되어야 한다.<br>
즉, 빠르고 실용적이지만 최신성이 중요하다.

<br>

### 2.5.5 문제 내역서

문제 내역서(problem statement)는 성능 문제를 처음 마주쳤을 때 가장 먼저 해야 할 기본 작업이다.<br>
문제가 왜 문제라고 느껴졌는지, 최근 변경 사항이 있었는지, 지연시간으로 표현할 수 있는지, 다른 사용자에게도 영향을 주는지, 현재 환경과 버전은 어떤지 등을 먼저 묻는 방식이다.<br>
이 질문들만으로도 원인과 해결책이 빠르게 드러나는 경우가 많다. 그래서 다른 방법론으로 들어가기 전에 문제 내역서를 명확히 만드는 것이 가장 먼저 해야 할 일이다.

<br>

### 2.5.6 과학적 방법론

과학적 방법론은 질문, 가설, 예측, 테스트, 분석의 순서로 진행된다.<br>
즉, 문제를 보고 원인을 추정한 뒤, 관찰이나 실험으로 그 가설을 검증하는 방식이다.<br>
예를 들어 메모리가 줄어든 뒤 성능이 나빠졌다면 "파일 시스템 캐시가 줄어들어 미스율이 증가했다"는 가설을 세울 수 있다.<br>
그다음 캐시 미스율을 비교하거나 캐시 크기를 바꿔보는 테스트를 통해 예측이 맞는지 확인하는 식이다.

<br>

이 방법의 장점은 문제를 바로 단정하지 않고, 검증 가능한 가설로 바꿔서 접근한다는 점이다.<br>
틀린 가설도 배제해 가며 조사 범위를 좁힐 수 있기 때문에, 복잡한 문제일수록 유용하다.

<br>

### 2.5.7 진단 사이클

진단 사이클은 과학적 방법론과 비슷하지만, 가설과 계측과 데이터를 더 빠르게 순환시키는 방식이다.<br>
흐름은 "가설 -> 계측 -> 데이터 -> 새로운 가설"로 이어진다.<br>
성능 분석은 데이터를 얻을 때마다 가설을 다듬어 가는 과정이라고 볼 수 있다.<br>
핵심은 틀린 가설에 오래 머물지 않고, 가능한 한 빨리 데이터로 넘어가서 더 나은 가설로 이동하는 것이다.

<br>

### 2.5.8 도구 방법론

도구 방법론은 먼저 사용 가능한 성능 도구를 나열하고, 각 도구가 제공하는 지표와 그 해석 방법을 정리하는 방식이다.<br>
이렇게 하면 어떤 도구를 어떤 순서로 쓸지에 대한 일종의 처방전을 만들 수 있다.<br>
실제로는 꽤 유용할 수 있지만, 사용 가능한 도구에만 의존한다는 한계가 있다.<br>
즉, 지금 손에 잡히는 도구가 보여주는 것만 보게 되기 때문에, 맞춤형 계측이나 새로운 관찰이 필요한 문제는 놓칠 수 있다.<br>
그래서 이 방법은 출발점이 될 수는 있어도, 완전한 방법론이 되기 어렵다.

<br>

### 2.5.9 USE 방법론

USE 방법론은 성능 검토 초기에 시스템 병목을 찾기 위한 대표적인 방법론으로, 모든 자원에 대해 사용률(Utilization), 포화도(Saturation), 오류(Errors)를 확인하는 방식이다.<br>
이 방법은 도구가 아니라 자원을 기준으로 생각한다는 점이 핵심이다.<br>
여기서 자원은 CPU, 메모리, 네트워크 인터페이스, 저장 장치, 컨트롤러, 인터커넥트 같은 하드웨어뿐 아니라 경우에 따라 락, 스레드 풀, 파일 디스크립터 같은 소프트웨어 자원도 포함할 수 있다.<br>
사용률은 자원이 얼마나 바쁜지, 포화도는 처리하지 못하고 쌓인 작업이 얼마나 있는지, 오류는 성능 저하를 일으킬 수 있는 실패 이벤트가 있는지를 본다.

<br>

오류를 먼저 보고, 그다음 포화도, 마지막으로 사용률을 해석하는 절차를 따르는 것이 좋다.<br>
오류는 비교적 해석이 쉽고, 포화도는 조금만 있어도 문제 신호가 될 수 있기 때문이다.<br>
이후 각 자원에 대해 사용할 지표를 정리하고, 측정할 수 없는 항목은 "모른다는 것을 아는 것"으로 기록해 두는 것이 좋다.

<br>

USE 방법론은 전체 자원을 빠르게 훑어보며 병목 후보를 찾는 데 강하다.<br>
특히 CPU 포화, 메모리 부족, 네트워크 인터페이스 사용률, 디스크 사용률처럼 비교적 쉽게 측정 가능한 지표에서 많은 문제를 발견할 수 있다.<br>
또한 클라우드의 리소스 제한이나 마이크로서비스 환경처럼 물리 자원 외의 제약도 같은 사고방식으로 볼 수 있다는 점이 장점이다.

<br>

### 2.5.10 RED 방법론

RED 방법론은 서비스, 특히 마이크로서비스나 클라우드 서비스의 상태를 사용자 관점에서 확인하는 방법론이다.<br>
모든 서비스에 대해 요청률(Request rate), 오류(Errors), 지속 시간(Duration)을 확인하는 것이 핵심이다.<br>
요청률은 초당 요청 개수, 오류는 실패한 요청 수, 지속 시간은 요청 완료까지 걸린 시간이다.<br>
RED 방법론은 USE처럼 빠르고 단순하면서도 포괄적인데, USE가 시스템 자원 상태를 보는 데 강하다면 RED는 사용자가 느끼는 서비스 상태를 보는 데 강하다.<br>
또한 요청률과 지속 시간을 함께 보면 부하 문제와 아키텍처 문제를 구별하는 데 도움이 된다.<br>
요청률은 비슷한데 지속 시간만 늘어나면 구조적 문제일 가능성이 있고, 요청률과 지속 시간이 함께 증가하면 부하 문제일 가능성이 크다.

<br>

### 2.5.11 워크로드 특성화

워크로드 특성화는 성능 결과보다 입력 부하 자체에 초점을 맞추는 방법론이다.<br>
시스템이 구조적으로 문제없더라도, 처리 한계를 넘는 부하가 들어오면 그 자체로 성능 문제를 만들 수 있기 때문이다.<br>
"누가", "왜", "무엇을", "어떻게"라는 질문으로 워크로드를 파악해 보면 좋다.<br>
누가 부하를 만들었는지, 어떤 호출 경로로 왔는지, I/O 유형이나 크기 같은 특성이 무엇인지, 시간에 따라 어떤 패턴을 보이는지 살펴보는 식이다.

<br>

이 과정을 통해 뜻밖의 원인을 발견할 수 있다.<br>
예를 들어 웹 서버만 데이터베이스를 사용한다고 생각했는데, 실제로는 외부에서 직접 접근이 들어와 DoS 성격의 부하를 만들고 있을 수도 있다.<br>
불필요한 부하를 줄이는 것만으로도 큰 성능 향상을 얻을 수 있기 때문에, 워크로드 특성화는 매우 실용적이다.

<br>

### 2.5.12 드릴다운 분석

드릴다운 분석은 높은 수준에서 시작해 점점 초점을 좁혀가며, 관심 영역을 더 깊게 파고드는 방식이다.<br>
모니터링, 식별, 분석의 세 단계로 이뤄지며, 최종적으로 근본 원인을 찾을 때까지 소프트웨어 스택의 아래쪽으로 내려간다.<br>
모니터링 단계에서는 장기간 지표를 수집해 이상 징후를 발견하고, 식별 단계에서는 CPU나 메모리 같은 특정 자원이나 영역으로 문제를 좁힌다.<br>
분석 단계에서는 트레이싱, 프로파일링, 맞춤형 계측, 소스 코드 확인 등을 통해 원인을 더 깊게 확인한다.<br>
여기에 "다섯 번 왜(Five whys)" 같은 질문 기법을 함께 사용할 수 있다.<br>
왜 이런 현상이 생겼는지를 반복해서 묻다 보면, 겉으로 드러난 증상이 아니라 메모리 파편화 같은 더 근본적인 원인까지 도달할 수 있다.

<br>

### 2.5.13 지연시간 분석

지연시간 분석은 어떤 연산의 전체 지연시간을 더 작은 구성 요소들로 나누고, 그중 더 느린 부분을 계속 따라가며 분석하는 방법론이다.<br>
일종의 이진 탐색처럼 느린 쪽을 계속 쪼개 내려간다고 볼 수 있다.<br>
예를 들어 데이터베이스 쿼리라면 먼저 전체 쿼리 처리 시간에서 CPU 시간과 대기 시간을 나누고, 대기 시간 안에서 파일 시스템, 락, 디스크 I/O 같은 항목으로 더 나눈다.<br>
그 후 디스크 I/O 안에서도 대기 시간인지 처리 시간인지, 처리 시간 안에서는 초기화 비용인지 데이터 전송 비용인지 계속 좁혀 들어간다.<br>
이 방법은 단순히 느리다는 사실을 확인하는 데서 그치지 않고, 정확히 어느 구간이 지연의 대부분을 차지하는지 정량적으로 밝히는 데 강점이 있다.

<br>

### 2.5.14 R 방법론

R 방법론은 오라클 데이터베이스를 위해 개발된 성능 분석 방법론으로, 트레이스 이벤트를 기반으로 지연시간 원인을 찾는 데 초점을 맞춘다.<br>
응답 시간 기반으로 가장 많은 시간을 소모하는 부분을 식별하고 수치화하는 것이 핵심이다.<br>
비록 오라클 데이터베이스 맥락에서 발전했지만, "가장 많은 시간을 쓰는 곳을 찾고 그것을 정량화한다"는 사고방식 자체는 다른 시스템에도 적용할 수 있다.

<br>

### 2.5.15 이벤트 트레이싱

시스템은 CPU 명령어, 디스크 I/O, 네트워크 패킷, 시스템 콜, 라이브러리 호출, 트랜잭션, 쿼리 같은 수많은 이벤트를 처리하며 동작한다.<br>
이벤트 트레이싱은 이런 개별 이벤트를 직접 기록해서 성능을 이해하는 방법론이다.<br>
평균 지연시간이나 스루풋 같은 요약 지표는 편리하지만, 중요한 세부사항을 숨길 수 있다.<br>
반면 이벤트 단위로 보면 각 요청의 입력, 시작 시간과 종료 시간, 결과와 오류 상태까지 직접 확인할 수 있어서 문제를 더 정확히 볼 수 있다.

<br>

예를 들어 네트워크는 `tcpdump`, 디스크 I/O는 `biosnoop`, 시스템 콜은 `strace`나 `perf trace` 같은 도구로 이벤트를 추적할 수 있다.<br>
특히 과거 이벤트와의 관계까지 보면, 현재 느린 요청이 사실은 자기 자신 때문이 아니라 앞선 요청들 때문에 대기열 뒤에 밀린 결과라는 것도 파악할 수 있다.

<br>

### 2.5.16 기준 통계

기준 통계(baseline statistics)는 시스템이 정상 상태일 때의 주요 성능 지표를 미리 수집해 두고, 이후 문제 상황과 비교하는 방법론이다.<br>
현재 값만 보면 그것이 좋은지 나쁜지 판단하기 어려운 지표가 많다.<br>
이럴 때 과거의 정상 상태와 직접 비교할 수 있는 기준 값이 있으면, 성능 변화의 크기와 방향을 훨씬 명확하게 볼 수 있다.<br>
커맨드 라인 도구, `/proc` 기반 통계, 프로파일링, 트레이싱 결과까지 포함해 기준 통계를 수집할 수 있다고 설명한다.<br>
단, 이런 수집 자체가 오버헤드를 만들 수 있으므로 프로덕션 환경에서는 주의가 필요하다.

<br>

### 2.5.17 정적 성능 튜닝

정적 성능 튜닝은 부하가 걸린 상태의 동적 성능이 아니라, 시스템 아키텍처와 설정 자체가 적절한지를 점검하는 방식이다. 시스템이 유휴 상태일 때도 할 수 있는 성능 점검이다.<br>
예를 들어 네트워크 인터페이스가 기대보다 낮은 속도로 협상된 경우, RAID 디스크 중 일부가 고장난 경우, 운영 체제나 애플리케이션 버전이 너무 오래된 경우, 파일 시스템이 거의 가득 찬 경우, 디버그 모드가 켜진 경우 등이 여기에 해당한다.<br>
정적 튜닝은 복잡한 원인 분석보다 먼저 확인해볼 만한 기본 점검 항목들을 제공한다는 점에서 실용적이다.

<br>

### 2.5.18 캐시 튜닝

캐시 튜닝은 애플리케이션에서 디스크에 이르는 여러 계층의 캐시를 점검하고 조정하는 방법론이다.<br>
가능한 한 스택의 상위 계층, 즉 작업이 실제로 일어나는 위치에 가까운 곳에 캐시를 두는 것이 더 효과적이다.<br>
캐시 튜닝에서는 먼저 캐시가 실제로 활성화되어 있는지, 히트율과 미스율은 어떤지, 시간당 미스 횟수는 얼마인지, 현재 캐시 크기는 적절한지를 확인해야 한다.<br>
그다음 워크로드에 맞게 캐시 파라미터를 조정하고, 불필요한 중복 캐싱이 있는지도 점검해야 한다.<br>
또한 모든 캐시가 같은 성능 효과를 주는 것은 아니다.<br>
CPU L1 캐시 조정보다 L3 캐시 조정이 더 큰 효과를 주는 것처럼, 어느 계층을 튜닝하느냐에 따라 얻는 성능 향상 폭이 달라질 수 있다.

<br>

### 2.5.19 마이크로 벤치마킹

마이크로 벤치마킹은 단순하고 인공적인 부하를 반복적으로 실행해 특정 구성 요소의 성능을 측정하는 방식이다.<br>
실제 사용자 워크로드를 흉내 내는 매크로 벤치마킹보다 훨씬 단순하고 이해하기 쉽다.<br>
예를 들어 시스템 콜 실행 시간, 파일 시스템 I/O, 네트워크 스루풋처럼 한정된 작업을 반복 측정해 평균 시간을 구할 수 있다.<br>
이 방식은 복잡한 실제 환경 전체를 재현하지는 않지만, 특정 요소의 한계나 병목을 빠르게 파악하는 데 유리하다.<br>
가능하다면 전용 마이크로 벤치마크 도구를 쓰고, 다른 관측 도구로 결과를 다시 검증하는 것이 안전하다.

<br>

### 2.5.20 성능 최적화를 위한 지침

성능 최적화 지침은 가장 효과적인 것부터 덜 효과적인 것 순으로 행동 원칙을 정리한 일종의 성능 규칙이다.<br>
핵심은 다음과 같다: 하지 마라, 하되 반복하지 마라, 덜 해라, 나중에 해라, 눈에 띄지 않게 해라, 동시에 해라, 더 저렴하게 해라.<br>
각 항목은 각각 불필요한 작업 제거, 캐싱, 갱신 빈도 축소, write-back 같은 지연 처리, 피크 시간 회피, 병렬 처리, 더 빠른 하드웨어 사용으로 이어진다.<br>
즉, 성능 최적화는 단순히 코드를 더 빠르게 짜는 문제가 아니라, 일을 없애고, 줄이고, 늦추고, 숨기고, 병렬화하고, 필요하면 하드웨어를 바꾸는 순서로 접근하라는 뜻이다.
