# CHAP 01 

## 1.1
* 시스템 성능 분석의 일반적인 목표: 
    * 지연 시간을 줄여 최종 사용자 경험을 개선, 컴퓨팅 비용을 절감하는 것 
    * 비효율성 제거, 시스템 throughput 향상
    * 시스템 전반 튜닝하여 비용 절감 가능 
* full stack: system 성능에 대해 이야기할때는 애플리케이션~하드웨어(metal) 에 이르기까지 시스템 라이브러리, 커널 및 하드웨어 자체까지 포함하는 전체 소프트웨어 스택 의미

## 1.2
* 일부 회사들은 performance engineer 라는 직책을 두어 시스템 성능에 집중하도록 함 
    * 복잡한 성능 문제 해결 
    * 성능 분석과 전체 환경에 대한 수용량 계획을 위한 더 나은 도구를 찾고 개발하는 핵심적 역할 수행 

## 1.3
* 성능 엔지니어링은 가능하면 하드웨어 선택이나 소프트웨어 작성 전부터 시작해야함 
* 클라우드 컴퓨팅은 초기 단계 건너뛰고 바로 개념 증명 테스팅(POC) 수행할 수 있도록 제공함 
    * canary testing 
    * blue-green deployment 
* capacity planning: 설계가 목표 성능 충족가능한지 평가함 
    * 설계 단계: 개발 중인 소프트웨어의 자원 사용량 분석 
    * 배포 후 실제 자원 사용량 지속적 모니터링 
        * 문제가 발생하기 전 예측

## 1.4 
* 성능 분석의 2가지 관점
    1. workload: 작업 부하의 성능을 책임지는 애플리케이션 개발자들이 주로 사용 
    2. resource : 시스템 자원을 관리하는 시스템 관리자들이 주로 사용

## 1.5 
시스템 성능 엔지니어링은 주관이 개입할 여지가 있고, 복잡하며 단일 원인으로 설명되지 않는 경우가 많음 
### 1.5.1 주관성 
* 버그는 객관적인 반면, 성능은 주관적인 면이 꽤 많음 
    * example) 평균 디스크 응답 I/O 시간은 1ms 이다 -> 좋을까? 나쁠까? (주관적 요소 있음)
    * 이러한 주관성은 목표를 명확하게 설정함으로써 객관화 가능 

### 1.5.2 복잡성 
* 시스템 자체의 복잡성과 분석을 어디서부터 시작해야할지 명확하지 않음 
* cascading failure: 한 구성 요소의 오류가 다른 구성 요소에 성능 문제를 일으키는 것 
* 시스템의 복잡성과 별도로 프로덕션 워크로드의 복잡한 특성이 성능 문제를 일으킬 수도 있음 
* 종합적인 접근법이 필요할 때도 있음 
* 다양한 방법론이 사용될 수 있다 

### 1.5.3 복합 원인 
* 여러 요인이 복합적으로 작용하여 발생 가능 

### 1.5.4 여러 성능 문제 
* 이미 알려졌으나 아직 해결되지 않은 성능 문제가 다수 존재함 
* 실제 과제는 성능상 문제를 찾는게 아니라 어떤 문제나 문제들이 가장 문제가 되는지 식별하는 것 
* => 각 문제의 규모를 정량화할 수 있어야함 

## 1.6
지연시간은 기다리는데 소요된 시간을 측정하는 것. 필수 성능 지표로 널리 사용됨 
* 넓은 의미: 특정 작업이 완료되는데 걸리는 시간 
* 지연시간은 최대 속도 향상을 추정할 수 있게 해주는 지표가 될 수 있음
    * 속도 향상 추정치 
        * example) 쿼리가 100ms 지연시간 소요됨. 이 중 80ms는 디스크 읽기 기다리느라 대기 => 디스크 읽기를 없애거나 캐싱을 통해 개선 가능하다면, 최대로 얻을 수 있는 성능향상은 100ms~20ms임 (최대 5배)
* 지연시간은 구체적인 맥락을 정의하지 않으면 모호할 수 있음 
    * 네트워크에서 지연시간 vs. 데이터 전송 시간을 포함한 전체 연결 지속 시간.. 
    * 연결 지연시간(connection latency): 네트워크에서 연결을 수립하는데 걸리는 시간
    * 요청 지연시간(request latency): 데이터 전송 시간을 포함한 전체 연결 지속 시간 

## 1.7
관측가능성(Observability) : 관찰을 통해 시스템을 이해하는 능력, 이를 가능하게 하는 도구들 
* 카운터, 프로파일링, 트레이싱.. 
* 벤치마크 도구는 해당 x
    * 벤치마크 도구들이 워크로드 실험을 통해 시스템 상태를 변화시키기 때문 
    * 프로덕션 환경에서는 실험 도구들이 resource contention을 일으켜 워크로드에 영향 미칠 수 있으므로 가급적이면 관측가능성 도구들을 우선적으로 사용하는 것이 좋음 
        * 반대로 유후 상태의 테스트 환경이면 하드웨어 성능 확인 위해 벤치마킹 도구를 먼저 사용하는 것이 유용할 수 있음 
### 1.7.1 카운터, 통계, 지표 
* 카운터: 애플리케이션, 커널은 자신들의 상태, 활동에 관한 데이터를 제공함 -> 소프트웨어 내에 하드코딩된 카운터라는 정수 변수로 구현됨 
    * 시간에 따른 변화율, 평균값, 백분위수 등의 통계 계산 가능 
* 지표(metric): 대상을 평가하고 모니터링하기 위해 선정된 통계 
    * 측정된 지표를 그래프로 나타낼 수 있음 -> Grafana

### 1.7.2 프로파일링
* 프로파일링(profiling): 샘플링을 수행하는 도구의 사용 
    * 일부 측정값을 샘플로 잡아서 대상의 전반적인 상태를 대략적으로 파악하는 방식
    * 가장 흔한 프로파일링 대상: CPU 
* CPU 프로파일링은 대개 정해진 시간 간격(time-interval)마다 cpu에서 실행되는 코드 경로를 샘플링하여 사용 패턴을 파악하는 식으로 진행됨 
* flame graph: CPU 프로파일링 데이터를 효과적으로 분석할 수 있는 시각화 도구 
    * 시간에 따른 CPU 사용량 변화를 시각적으로 표현 가능 
    * 단순한 CPU 문제 뿐만 아니라 사용 패턴을 통해 다양한 유형의 문제 식별 가능 

### 1.7.3 트레이싱
* 트레이싱(tracing)은 시스템 내에서 발생하는 이벤트들을 기록하고 추적하는 과정 
    * 수집된 이벤트 데이터는 저장되어 추후 분석에 활용되거나 실시간으로 사용자가 원하는 요약 정보나 다른 처리를 위해 쓰일 수 있음 
    * 예시 도구들: 
        * 리눅스 strace(1): 시스템 콜을 트레이싱 
        * 리눅스 tcpdump(8): 네트워크 패킷을 트레이싱하기 위한 특수 목적 도구 
        * 모든 소프트웨어/하드웨어 이벤트의 실행을 분석할 수 있는 범용 트레이싱 도구 (Ftrace, BCC, bpftrace)도 있음 
            * 정적, 동적 계측 
            * 프로그래밍을 위해 BPF와 같은 다양한 이벤트 소스를 활용함 
* 정적 계측 : 소스코드에 하드코딩된 소프트웨어 계측점 
    * 리눅스에서 커널 정적 계측 기술은 tracepoint
    * 사용자 공간 소프트웨어의 정적 계측 기술은 USDT(User statically defined tracing)
        * libc와 같은 라이브러리에서 함수 호출을 계측하거나 여러 애플리케이션에서 서비스 요청을 계측하는데 사용됨 
    * 예시: execsnoop(8)
        * execve(2) 시스템 콜을 추적하는 tracepoint를 계측하여 
        * 트레이싱(실행)하는 동안 생성된 새로운 프로세스들을 출력함 
* 동적 계측: 소프트웨어 실행 중에 계측점을 생성하는 방식 
    * 메모리 내의 명령어를 수정하여 계측 루틴을 삽입함 
    * 실행 중인 어떤 소프트웨어에서도 사용자 맞춤형 성능 통계 생성할 수 있게 해줌 
    * DTrace
* BPF 
    * 리눅스의 최신 동적 트레이싱 도구를 구동하는 핵심 기술로 발전함 
    * BCC(BPF Compiler Collection, BPF 컴파일러 모음)와 bpftrace 프론트엔드 사용해 프로그래밍 가능 


## 1.8 실험 
* 관측가능성 도구와 별개로 실험 도구들도 존재 
* 벤치마킹 도구 
    * 인공적인 워크로드를 시스템에 적용하고 성능을 측정하는 방식으로 실험을 수행함 
        * 실험 도구가 테스트 중인 시스템 성능 교란시킬 수 있으므로 주의해야함 
    1. macro-benchmark: 클라이언트가 애플리케이션 요청을 발생시키는 것과 같은 실제 환경의 작업 부하를 시뮬레이션
    2. micro-benchmark: CPU, 디스크, 네트워크 등과 같은 특정 구성 요소를 개별적으로 테스트 
        * 디버깅이 쉽고, 결과를 반복해 확인하기 용이하며 이해하기 쉽고 더 안정적 
* 프로덕션 시스템에서는 우선 관측 도구를 사용해 문제 분석하는 것이 좋음 
    * but 관측 도구가 많기 때문에 실험 도구가 더 빠른 결과를 제공할 수 있음에도 이 도구들로 작업하느라 시간 허비할 수 있음 -> 알아서 잘 판단해서 사용해라는 의미 같음 

## 1.9 클라우드 컴퓨팅 
* 클라우드 컴퓨팅은 수요에 따라 컴퓨팅 자원을 배포하는 방식 
    * 엄격한 용량 계획의 필요성을 줄여줬음 
    * 그러나 성능 분석의 필요를 높이는 측면도 있다 
        * 성능 향상으로 더 적은 시스템을 사용할 수 있다면 -> 즉시 비용 절감의 효과! 
* 클라우드 컴퓨팅, 가상화로 인해 새롭게 발생한 어려움: 다른 tenant가 성능에 미치는 영향 관리(or performance isolation) 
    * 각 테넌트가 다른 사용자의 물리적 시스템을 보지 못하도록 막는 일 
    * 예시: 시스템이 적절히 관리되지 않으면 이웃 테넌트와의 경쟁으로 인해 디스크 I/O 성능이 저하될 수 있음 
    * 테넌트?: 공용 it 인프라 내에서 논리적으로 구분된 자원을 사용하는 독립된 사용자 그룹 

## 1.10 방법론 
방법론은 시스템 성능을 분석할 때 권장되는 단계를 문서화하는 방법 -> 효율적이고, 중요한 부분을 놓치지 않도록 도움

### 1.10.1 60초 리눅스 성능 분석 
성능 문제 조사 시작 60초 동안 수행할 수 있는 리눅스 도구 기반 체크리스트 
* uptime: 부하 평균을 통해 부하가 증가하는지/감소하는지 확인 
* dmesg - T | tail : 커널 오류 
* vmstat -SM 1 : 시스템 전체에 대한 통계
* mpstat -P ALL 1: CPU별 부하 균형
* pidstat 1: 프로세스별 cpu 사용률 조사 
* iostat -sxz 1: 디스크 i/o 통계 파악
* free -m: 메모리 사용률 체크 
* sar -n DEV 1: 네트워크 장치 i/o 검사 
* sar -n TCP,ETCP 1: TCP 통계 분석
* top : 전체 개요 확인 

## 1.11 사례 연구 
시스템 성능 분석에 익숙하지 않을때 어떤 성능 개선 작업이 왜, 언제 필요한지 보여주는 사례 연구가 도움이 될 수 있음 

### 1.11.1 느린 디스크 
* 최근에 1,000밀리초를 초과하는 쿼리 로그가 여럿 발생. 지난주부터 시간당 수십건 발생 중. AcmeMon을 통해 디스크 사용률이 높은 것을 확인함 
    * AcmeMon은 회사에서 사용하는 기본 서버 모니터링 시스템(가상의 도구임.)
        * 운영체제가 제공하는 표준 성능 지표를 기반으로 하고 있음 : mpstat(1), iostat(1)
* USE 방법론을 사용하여 자원 병목의 지점을 신속하게 찾는 것부터 시작함 
    * 디스크의 사용률은 80%정도 높았지만 다른 자원들은 사용률이 훨씬 낮았음 
    * 과거 데이터는 지난주에 디스크 사용률이 지속적으로 증가해왔지만 CPU 사용률은 일정했음을 확인 
* AcmeMon은 디스크의 포화 상태나 오류, 통계를 제공하지 않기 때문에 방법론 수행을 위해 서버에 직접 접속하여 몇가지 명령을 실행함 
    * /sys에서 디스크 오류 카운터 검사: 오류 x 
    * iostat(1)을 실행해 시간이 지남에 따라 디스크의 활용도, 포화도 지표가 어떻게 변하는지 1초 단위로 살펴봄 
    * AcmeMon에서는 1분 단위로 80% 사용률 보고했으나 1초 단위로 살펴본 결과 디스크 사용률의 변화가 심하게 변동하며 자주 100%에 도달 -> 이로 인해 포화 상태가 발생하여 디스크 I/O 지연 시간이 증가함을 발견 
* 왜 디스크 부하가 증가하는가? 
    * 디스크 성능 통계를 살펴본 결과 높은 부하 상태에서 디스크가 정상적으로 작동하고 있음 확인 
    * 워크로드 특성 분석 시작 
    * iostat(1)을 사용해 IOPS, throughput, 평균 디스크 I/O 지연시간, 읽기/쓰기 비율 측정함 
    * 디스크 부하가 높아서 I/O 지연 시간이 증가 -> 쿼리 속도가 느려짐 
* 디스크 I/O의 정확한 원인 파악 위해 drill-down analysis 수행? -> 시간이 오래걸림 
* 대신 디스크 I/O가 주로 파일 시스템 캐시(페이지 캐시) 미스로 인해 발생한다는 것을 기억 -> cachestat(8) 사용하여 파일 시스템 캐시 히트율 확인 
    * 그러나 높았음. 비슷한 워크로드 처리하는 다른 데이터베이스 확인해도 높았음 
* 개발 프로젝트의 프로토타입 애플리케이션이 메모리를 많이 잡아먹고 있었음 -> 캐시 히트율이 낮아지게 됨 -> 디스크 읽기 증가시킴 

### 1.11.2 소프트웨어 변경 
* 새 애플리케이션 프로덕션 배포 전 non-regression 테스트 
* 테스트 서버를 현재 배포 구성에 맞게 설정 
    * 클라이언트 부하 시뮬레이터를 다른 시스템에서 대상 시스템으로 실행함
    * 클라이언트 워크로드의 특성은 액세스 로그를 통해 확인 가능 
        * 결과적으로 평균적으로는 프로덕션과 비슷한 부하를 가지지만 변동성은 반영하지 못함 -> 기록해두고 분석 진행 
* stress test 진행
    * 클라이언트 시뮬레이터로 서버가 한계에 도달할 때까지 부하를 점차 늘려가는 방법 
        * 클라이언트 시뮬레이터는 초당 클라이언트 요청 횟수 설정 가능 
            * 초반에 기본값 1,000요청/초 사용함 
            * 좀 더 정밀한 결과 얻기 위해 100요청/초에서 시작해 100요청/초씩 증가시킴 
            * 한계에 도달할때까지 각 부하 수준을 1분씩 실험 
    * 테스트를 자동으로 실행하고 결과를 파일로 수집하는 셸 스크립트 작성함 -> 다른 도구로 시각화할 예정 
* 부하를 가한 상태에서 제약 요인 파악 위해 능동적 벤치마크 수행 
    * 서버 자원은 대체로 유휴 상태 
    * 클라이언트 시뮬레이터는 요청 처리량이 초당 약 700에서 한계점에 도달해 수렴 
* 새 소프트웨어 버전으로 전환하여 동일 테스트 반복 
    * 이번에도 700요청/초 지점에서 수렴함 
    * 제약 요인 x 
* 실험 결과를 부하 대비 시간당 완료된 요청 그래프로 그려서 확장성 프로필을 시각적으로 비교 -> 눈에 띄는 차이 없었음 
* 딱히 다른 제약 요인이 없었음.. -> 서버 리소스만을 검토했기 때문에 애플리케이션 로직의 문제 or 네트워크 or 클라이언트 시뮬레이터와 같은 다른 요인에 의할 것이다 => 다른 접근 방식 시도

* 일정한 속도로 연산 실행 후 자원 사용률로 표현하는 접근 방식 
    * 시뮬레이터를 초당 700요청으로 설정하고 현재와 새 소프트웨어에서 자원 소비량을 측정함 
    * 같은 부하에 대해 현재 소프트웨어는 32개의 cpu를 평균 20% 사용 
    * 새 소프트웨어는 동일한 부하에 대해 같은 cpu에서 30%의 사용률 
    * 더 많은 cpu 자원을 소비하기 때문에 새 소프트웨어가 약간 퇴행? 
* 700요청/초의 한계 원인? 
    * 더 높은 부하를 실험하여 네트워크, 클라이언트 시스템, 클라이언트 부하 발생기 포함한 모든 데이터 경로 검토함 
    * 서버와 클라이언트 소프트웨어에 대해 드릴다운 분석 수행 
    * 체크한 내용을 나중에 참조할 수 있도록 화면 캡처와 함께 문서로 정리함 
* 클라이언트 소프트웨어(시뮬레이터) 조사
    * 상태 분석 실시 -> 소프트웨어가 단일 스레드로 구성되어있음 확인 
    * 단일 스레드가 한 cpu에서 100% 사용률 보임 => 제약의 원인! 
* 실험삼아 여러 클라이언트 시스템에서 클라이언트 소프트웨어 병렬로 실행시킴 
    * 현재, 새 소프트웨어 모두에서 서버 cpu 사용률을 100%까지 끌어올림 
    * 현재는 초당 3,500개, 새 버전은 2,300개의 요청을 처리 
* 새 소프트웨어 버전에서 성능 저하가 발생했다 
    * 성능 저하 원인 찾기 위해 cpu 플레임 그래프 사용해 cpu 사용을 프로파일링하여 관련 코드 경로를 탐색함 
    * 평균적인 프로덕션 부하만 테스트되었고, 변동성 있는 부하는 테스트 되지 않았음을 기록함 
    * 클라이언트 부하 발생기가 단일 스레드로 동작하므로 이것이 병목 지점이 될 수 있다는 점도 버그로 보고함
