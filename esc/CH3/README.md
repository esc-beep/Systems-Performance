# 3장. 운영 체제

<br>

## 3.1 용어

- 운영 체제(operating system): 시스템을 부팅하고 프로그램을 실행하기 위해 필요한 소프트웨어 전체를 뜻한다. 커널뿐 아니라 시스템 라이브러리, 관리 도구, 기본 유틸리티까지 포함하는 넓은 개념이다.
- 커널(kernel): 운영 체제의 핵심 프로그램이다. CPU 스케줄링, 메모리 관리, 파일 시스템, 네트워크, 장치 접근처럼 특권이 필요한 일을 담당한다.
- 프로세스(process): 실행 중인 프로그램의 추상화된 실행 환경이다. 고유한 주소 공간, 파일 디스크립터, 스레드 등을 가진다.
- 스레드(thread): 운영 체제가 CPU에 스케줄링할 수 있는 실행 단위이다. 하나의 프로세스는 여러 스레드를 가질 수 있고, 이들은 같은 주소 공간을 공유한다.
- 태스크(task): 리눅스에서 실행 가능한 단위를 가리키는 용어로, 문맥에 따라 프로세스나 스레드를 모두 포함해 부르기도 한다.
- BPF 프로그램: 커널 내부의 BPF 실행 환경에서 동작하는 프로그램으로, 관측가능성이나 네트워크 처리 같은 작업을 안전하게 확장하는 데 사용된다.
- 메인 메모리와 가상 메모리: 메인 메모리는 실제 RAM이고, 가상 메모리는 운영 체제가 제공하는 추상화된 주소 공간이다. 가상 메모리 덕분에 각 프로세스는 독립적인 메모리 공간을 가진 것처럼 동작한다.
- 커널 공간과 사용자 공간: 커널 공간은 커널이 사용하는 주소 공간이고, 사용자 공간은 일반 프로세스가 사용하는 주소 공간이다. 둘을 분리함으로써 안정성과 보안을 확보한다.
- 컨텍스트 스위치(context switch): 실행 중인 스레드나 프로세스에서 다른 실행 단위로 CPU를 전환하는 작업이다. 이 과정에서 레지스터, 스택 같은 실행 문맥이 교체된다.
- 모드 스위치(mode switch): 사용자 모드와 커널 모드 사이를 전환하는 것을 뜻한다. 시스템 콜을 호출할 때 대표적으로 발생한다.
- 시스템 콜(system call): 사용자 프로그램이 커널에게 특권 작업을 요청하는 표준 인터페이스이다.
- 프로세서(processor): 하나 이상의 CPU 코어를 포함하는 물리 칩을 뜻한다. 프로세스(process)와 이름이 비슷하지만 전혀 다른 개념이다.
- 트랩과 인터럽트: 트랩은 커널로 제어를 넘기기 위한 소프트웨어적 신호이고, 인터럽트는 하드웨어나 시스템 이벤트가 처리를 요구할 때 발생하는 신호이다.

<br>

## 3.2 배경지식

### 3.2.1 커널

커널은 운영 체제의 중심에서 하드웨어와 소프트웨어 사이를 연결하는 역할을 한다.<br>
리눅스와 BSD 같은 유닉스 계열 시스템은 보통 모놀리식 커널 구조를 사용하며, CPU 스케줄링, 메모리 관리, 파일 시스템, 네트워크 프로토콜, 장치 드라이버 같은 기능을 커널 안에서 수행한다.<br>
시스템 라이브러리는 사용자 프로그램이 시스템 콜을 더 편하게 호출할 수 있도록 감싼 인터페이스를 제공하지만, 필요하면 애플리케이션이 시스템 콜을 직접 사용할 수도 있다.

<br>

커널 구조에는 여러 변형이 있다.<br>
마이크로커널은 커널 크기를 줄이고 일부 기능을 사용자 모드로 빼내는 방식이고, 유니커널은 커널 코드와 애플리케이션을 하나로 묶는 방식이다.<br>
하이브리드 커널은 이 둘의 성격을 섞어 사용한다.<br>
최근에는 eBPF가 등장하면서 커널 안에서 안전하게 확장 코드를 실행할 수 있게 되었고, 이를 통해 기존 커널 기능을 더 유연하게 확장할 수 있게 되었다.

<br>

### 3.2.2 커널 및 사용자 모드

커널은 가장 높은 권한의 커널 모드에서 실행되고, 일반 프로그램은 제한된 권한의 사용자 모드에서 실행된다.<br>
장치 접근이나 메모리 보호처럼 위험한 작업은 사용자 프로그램이 직접 수행할 수 없고, 시스템 콜을 통해 커널에 요청해야 한다.<br>
이 권한 분리는 멀티태스킹과 보안을 가능하게 하는 핵심 장치다.

<br>

다만 사용자 모드와 커널 모드를 오가는 비용은 성능에 영향을 준다.<br>
그래서 운영 체제는 이를 줄이기 위한 다양한 기법을 발전시켜 왔다.<br>
예를 들어 `vDSO`는 일부 시스템 콜을 사용자 공간에서 더 싸게 처리하게 해주고, `mmap`은 메모리 매핑을 통해 복사와 호출 비용을 줄일 수 있게 해준다.<br>
또한 커널 우회(kernel bypass)나 커널 모드 애플리케이션 같은 방식은 특정 워크로드에서 더 높은 성능을 얻기 위해 전통적인 경로를 줄이거나 우회한다.

<br>

### 3.2.3 시스템 콜

시스템 콜은 사용자 프로그램이 커널에 기능을 요청하는 기본 인터페이스다.<br>
유닉스 철학은 시스템 콜 집합을 가능한 단순하고 일관되게 유지하려는 쪽에 가깝지만, 현대 리눅스는 다양한 기능을 지원하기 위해 매우 많은 시스템 콜을 제공한다.

<br>

대표적인 시스템 콜은 다음과 같다:
- 파일 I/O: `read(2)`, `write(2)`, `open(2)`, `close(2)`
- 프로세스/스레드 관리: `fork(2)`, `clone(2)`, `exec(2)`
- 네트워크 연결: `connect(2)`, `accept(2)`
- 메모리 관리: `mmap(2)`, `brk(2)`
- 동기화와 제어: `futex(2)`, `ioctl(2)`

<br>

이 중 `ioctl(2)`처럼 이름만 보고 역할을 바로 이해하기 어려운 시스템 콜도 있다.<br>
이런 인터페이스는 장치나 서브시스템마다 다양한 제어 명령을 하나의 창구로 처리하는 데 쓰인다.<br>
즉, 시스템 콜은 단순한 호출 목록이 아니라 운영 체제가 어떤 기능을 외부에 노출하는지 보여주는 설계의 흔적이기도 하다.

<br>

### 3.2.4 인터럽트

인터럽트는 현재 실행 중인 작업을 잠시 멈추고 다른 이벤트를 먼저 처리하게 만드는 메커니즘이다.<br>
디스크 I/O 완료, 네트워크 패킷 도착, 타이머 만료 같은 사건이 발생하면 프로세서는 해당 이벤트를 처리하기 위해 커널로 제어를 넘긴다.

<br>

인터럽트는 크게 두 종류로 나눌 수 있다:
- 비동기 인터럽트: 디스크, 네트워크 카드 같은 하드웨어 장치가 보내는 이벤트이다.
- 동기 인터럽트: 현재 실행 중인 명령과 직접 관련된 이벤트로, 시스템 콜, 예외, 페이지 폴트 등이 여기에 해당한다.

<br>

인터럽트 처리는 가능한 한 짧게 끝내는 것이 중요하다.<br>
그래서 리눅스는 전반부(top half)에서 급한 일만 처리하고, 나머지는 후반부(bottom half), 소프트IRQ, 워크 큐 같은 메커니즘으로 넘겨 지연을 줄인다.<br>
또한 데드락이나 일관성 문제를 막기 위해 특정 구간에서는 인터럽트를 잠시 마스킹하기도 하지만, 이 시간은 짧을수록 좋다.

<br>

### 3.2.5 클럭과 유휴 상태

초기 유닉스 커널은 주기적인 타이머 인터럽트에 크게 의존했다.<br>
이 클럭 루틴은 시스템 시간을 갱신하고, 타이머를 깨우고, 스레드의 타임 슬라이스를 관리하는 중요한 역할을 맡았다.

<br>

하지만 주기적인 틱은 두 가지 문제를 낳는다.<br>
첫째, 다음 틱까지 기다려야 타이머를 처리할 수 있어 추가 지연이 생길 수 있다.<br>
둘째, 틱 자체가 CPU를 깨우기 때문에 오버헤드와 전력 소모를 만든다.<br>
이를 줄이기 위해 현대 커널은 고해상도 타이머와 tickless 구조를 도입해 필요할 때만 깨우는 방향으로 발전했다.

<br>

CPU가 할 일이 없을 때는 유휴 스레드(idle task)가 실행된다.<br>
현대 프로세서는 이 상태에서 더 깊은 절전 모드로 들어갈 수 있고, 커널은 불필요한 틱을 줄여 이런 절전 상태가 오래 유지되도록 돕는다.

<br>

### 3.2.6 프로세스

프로세스는 프로그램이 실행되기 위한 환경이며, 주소 공간, 파일 디스크립터, 스레드, 각종 메타데이터를 포함한다.<br>
운영 체제는 이 프로세스들을 멀티태스킹 방식으로 번갈아 실행해 여러 작업이 동시에 돌아가는 것처럼 보이게 한다.

<br>

리눅스에서 프로세스는 보통 `fork()`와 `exec()` 흐름으로 생성된다.<br>
`fork()`는 현재 프로세스를 복제하고, 이후 `exec()`는 그 위에 새로운 프로그램 이미지를 올린다.<br>
복제 시에는 copy-on-write를 사용해 실제 복사를 미루므로 메모리와 CPU 비용을 줄인다.

<br>

프로세스는 실행 중(on-CPU), 실행 준비(run queue), 수면/대기, 좀비 상태 등 여러 상태를 오간다.<br>
또한 하나의 프로세스는 여러 스레드를 가질 수 있고, 스레드는 주소 공간과 파일 디스크립터를 공유하면서도 각각의 스택과 레지스터를 가진다.

<br>

### 3.2.7 스택

스택은 함수 호출 과정에서 임시 데이터를 저장하는 LIFO 구조의 메모리 영역이다.<br>
함수가 호출되면 리턴 주소와 일부 레지스터 값, 로컬 데이터가 스택 프레임 단위로 쌓인다.

<br>

이 스택 프레임들을 따라 올라가면 현재 코드가 어떤 경로를 통해 여기까지 왔는지 알 수 있는데, 이것이 스택 트레이스다.<br>
성능 분석에서는 스택 트레이스를 통해 CPU 시간을 많이 쓰는 경로, 시스템 콜 경로, 병목 함수 호출 체인을 파악할 수 있다.<br>
또한 시스템 콜 실행 중에는 사용자 스택과 커널 스택이 각각 따로 존재하므로, 어떤 문맥에서 실행 중인지 구분해 이해하는 것이 중요하다.

<br>

### 3.2.8 가상 메모리

가상 메모리는 각 프로세스가 자신만의 큰 주소 공간을 가진 것처럼 보이게 해주는 추상화다.<br>
이 덕분에 여러 프로세스가 서로 충돌하지 않으면서 동시에 실행될 수 있고, 실제 RAM보다 더 큰 메모리를 사용하는 것처럼 동작할 수도 있다.

<br>

운영 체제는 자주 쓰는 데이터를 메인 메모리에 남기고, 덜 중요한 데이터는 디스크로 밀어내는 방식으로 메모리를 관리한다.<br>
이때 초기 유닉스는 프로세스 전체를 교체하는 스와핑에 의존했지만, 이후 BSD 계열은 페이지 단위로 메모리를 옮기는 페이징을 도입해 훨씬 효율적으로 개선했다.<br>
리눅스에서 흔히 말하는 스왑도 실제로는 페이지 단위 교체를 의미하는 경우가 많다.

<br>

### 3.2.9 스케줄러

스케줄러는 어떤 스레드가 어떤 CPU에서 언제 실행될지를 정하는 커널의 핵심 구성 요소다.<br>
실행 준비가 된 스레드들을 관리하고, 우선순위와 정책에 따라 CPU 시간을 나눠준다.

<br>

워크로드를 크게 나누면 CPU-bound와 I/O-bound로 볼 수 있다.<br>
CPU-bound 작업은 긴 계산 시간이 중요하고, I/O-bound 작업은 빠른 응답성이 중요하다.<br>
전통적인 유닉스 스케줄러는 CPU를 오래 잡고 있는 작업의 우선순위를 낮춰 I/O 중심 작업과 대화형 작업이 더 빠르게 반응할 수 있도록 조정해 왔다.

<br>

현대 커널은 일반 스케줄링 외에도 실시간 스케줄링 클래스를 제공한다.<br>
이런 정책은 더 높은 우선순위와 선점 기능을 통해 예측 가능하고 낮은 지연시간을 요구하는 시스템을 지원한다.

<br>

### 3.2.10 파일 시스템

파일 시스템은 데이터를 파일과 디렉터리 구조로 정리해 제공하는 운영 체제의 핵심 기능이다.<br>
운영 체제는 루트(`/`)를 시작점으로 하는 전역 파일 네임스페이스를 제공하고, 서로 다른 파일 시스템을 마운트해서 하나의 트리처럼 보이게 만든다.

<br>

또한 VFS(Virtual File System)는 여러 파일 시스템을 공통 인터페이스로 추상화해 준다.<br>
덕분에 애플리케이션은 ext4, ZFS, NFS, `/proc`, `/dev`처럼 서로 다른 성격의 파일 시스템도 일관된 방식으로 접근할 수 있다.<br>
저장 장치 기반 환경에서는 애플리케이션에서 실제 디스크까지 이어지는 경로를 I/O 스택이라고 부르며, 성능 분석에서 중요한 관찰 지점이 된다.

<br>

### 3.2.11 캐싱

디스크 I/O는 전통적으로 매우 느렸기 때문에, 운영 체제와 소프트웨어 스택의 여러 계층은 읽기 캐시와 쓰기 버퍼링을 적극적으로 사용해 왔다.<br>
캐시는 브라우저, 웹 서버, 애플리케이션, 캐시 서버, 데이터베이스, 운영 체제 버퍼 캐시, 파일 시스템 캐시, 장치 컨트롤러, 디스크 자체에 이르기까지 여러 층에 걸쳐 존재할 수 있다.

<br>

핵심 아이디어는 비싼 디스크 접근을 피하고 더 빠른 계층에서 응답하는 것이다.<br>
예를 들어 최근에 읽은 디스크 블록이 버퍼 캐시에 남아 있다면 실제 디스크를 다시 읽지 않고도 즉시 처리할 수 있다.<br>
즉, 성능 문제를 볼 때는 캐시가 있는지 없는지만이 아니라 어느 계층의 캐시가 작동하고 있는지도 함께 봐야 한다.

<br>

### 3.2.12 네트워킹

현대 커널은 내장된 네트워크 프로토콜 스택을 제공하고, 애플리케이션은 소켓을 통해 이 스택에 접근한다.<br>
네트워크 인터페이스 카드(NIC)와 커널 드라이버, TCP/IP 스택, 소켓 API가 함께 네트워크 통신의 기반을 이룬다.

<br>

과거에는 인터페이스 주소를 수동으로 설정하는 일이 중요했지만, 오늘날에는 DHCP 같은 메커니즘이 이를 자동화한다.<br>
또한 QUIC처럼 새로운 전송 프로토콜이 등장하거나 혼잡 제어 알고리즘이 바뀌면, 사용자 공간만이 아니라 커널 지원 여부도 성능에 큰 영향을 줄 수 있다.

<br>

### 3.2.13 장치 드라이버

장치 드라이버는 커널이 하드웨어와 대화할 수 있게 해주는 소프트웨어다.<br>
드라이버는 장치를 제어하고 I/O를 수행하며, 필요에 따라 모듈 형태로 동적으로 로드되기도 한다.

<br>

장치 인터페이스는 크게 문자 장치와 블록 장치로 나눌 수 있다.<br>
문자 장치는 순차적인 I/O에 적합하고, 블록 장치는 정해진 크기의 블록 단위로 임의 접근이 가능하다.<br>
초기 유닉스는 블록 장치 성능을 높이기 위해 버퍼 캐시를 적극 활용했고, 리눅스는 이를 페이지 캐시에 통합해 발전시켰다.

<br>

### 3.2.14 멀티프로세서

멀티프로세서 시스템에서는 여러 CPU를 사용해 작업을 병렬로 처리할 수 있다.<br>
SMP는 여러 CPU를 동등하게 취급하는 전형적인 방식이지만, 실제로는 메모리 공유, 캐시 일관성, 락 경쟁 같은 문제 때문에 구현과 최적화가 쉽지 않다.

<br>

NUMA 구조에서는 어떤 메모리에 접근하느냐에 따라 지연시간이 달라진다.<br>
가까운 메모리는 빠르고 먼 메모리는 느리기 때문에, 스케줄링과 메모리 배치 전략이 성능에 큰 영향을 준다.<br>
또한 CPU 간 조율이 필요할 때는 IPI(Inter-Processor Interrupt)를 사용해 다른 CPU에 즉시 작업을 요청하기도 한다.

<br>

### 3.2.15 선점

선점(preemption)은 더 중요한 작업이 현재 실행 중인 작업을 중단하고 CPU를 차지할 수 있게 하는 메커니즘이다.<br>
실시간 시스템처럼 응답 지연을 엄격하게 관리해야 하는 환경에서는 특히 중요하다.

<br>

커널은 완전 선점형일 수도 있고, 자발적 선점형일 수도 있다.<br>
완전 선점형은 지연시간을 줄이는 데 유리하지만 구현 복잡성이 높고, 자발적 선점은 커널 코드 안의 정해진 지점에서만 선점을 허용해 복잡성을 줄이면서도 적당한 응답성을 제공한다.<br>
반대로 선점을 거의 허용하지 않는 설정은 스루풋에는 유리할 수 있지만 지연시간이 늘어날 수 있다.

<br>

### 3.2.16 자원 관리

운영 체제는 CPU, 메모리, 디스크, 네트워크 같은 자원을 세밀하게 제어할 수 있는 기능을 제공한다.<br>
이런 자원 제어는 여러 애플리케이션을 함께 실행하거나, 클라우드 환경에서 여러 테넌트의 성능을 안정적으로 분리할 때 특히 중요하다.

<br>

초기에는 `nice`나 `ulimit` 같은 단순한 수단이 중심이었지만, 리눅스는 `cgroups`를 도입하면서 훨씬 정교한 제어가 가능해졌다.<br>
`cgroups v2`는 이런 자원 관리 구조를 더 일관되게 정리한 버전으로, 현대 리눅스에서 핵심적인 자원 제어 수단으로 자리잡고 있다.

<br>

### 3.2.17 관측가능성 도구

운영 체제는 기본적으로 성능을 관찰하고 분석할 수 있는 다양한 도구를 제공한다.<br>
이 도구들은 커널, 라이브러리, 사용자 프로그램 위에 구축되며, 보통 `/usr/bin`, `/usr/sbin` 같은 경로에서 사용할 수 있다.

<br>

여기에 서드파티 도구까지 더하면 관측가능성은 더 확장된다.<br>
즉, 운영 체제를 이해한다는 것은 단순히 커널 구조만 아는 것이 아니라, 그 위에서 어떤 관찰 도구가 어떤 정보를 제공하는지도 함께 이해하는 것이다.

<br>

## 3.3 커널

이 절은 유닉스 계열 커널이 성능 관점에서 어떻게 발전해 왔는지를 비교해서 보여준다.<br>
파일 시스템, 시스템 콜, 네트워크 스택, 실시간 지원, CPU/디스크/네트워크 스케줄링 같은 요소는 커널마다 다르게 구현될 수 있고, 그 차이가 성능 특성의 차이로 이어진다.

<br>

또한 시간이 지나면서 커널이 점점 더 많은 기능을 품게 되었다는 점도 강조된다.<br>
초기 유닉스가 매우 적은 수의 시스템 콜로 시작했다면, 현대 리눅스는 수백 개의 시스템 콜을 제공한다.<br>
이는 기능 확장의 결과이기도 하지만, 동시에 학습과 디버깅의 복잡도가 커졌다는 의미이기도 하다.

<br>

### 3.3.1 유닉스

유닉스는 1969년 켄 톰슨, 데니스 리치, 그리고 벨 연구소 연구진이 만든 경량 멀티태스킹 운영 체제다.<br>
멀틱스에서 영향을 받았지만, 더 작고 단순하며 실용적인 시스템을 지향했다.

<br>

유닉스의 중요한 철학 중 하나는 커널이 제공하는 방식은 단순해야 한다는 점이다.<br>
옵션을 과도하게 늘리기보다, 적은 수의 기본 기능을 일관되게 제공하는 것이 중요하다고 봤다.<br>
그럼에도 유닉스는 높은 성능을 위해 우선순위 기반 스케줄링, 디스크 블록 I/O, 버퍼 캐시, 스와핑, 멀티태스킹 같은 기능을 갖추고 있었다.

<br>

이후 네트워킹, 다중 파일 시스템, 페이징 같은 기능이 추가되면서 유닉스 계열은 더 복잡해졌고, BSD, 솔라리스, 리눅스 같은 후속 시스템으로 분화해 갔다.

<br>

### 3.3.2 BSD

BSD는 유닉스를 바탕으로 버클리에서 발전한 계열로, 성능 측면에서 여러 중요한 혁신을 도입했다.<br>
대표적으로 가상 메모리의 페이징, 요구 페이징, Berkeley Fast File System, 고성능 TCP/IP 네트워크 스택, 소켓 API 등이 있다.

<br>

이 중 소켓과 TCP/IP 스택은 오늘날 네트워크 프로그래밍의 사실상 표준이 되었고, FFS는 파일 시스템 설계에 큰 영향을 주었다.<br>
또한 FreeBSD의 jails는 운영 체제 수준 가상화의 선구적인 형태로 볼 수 있고, 최근에는 커널 TLS처럼 네트워크 성능을 높이기 위한 기능도 제공한다.

<br>

BSD는 리눅스만큼 대중적이지는 않지만, CDN이나 고성능 파일 서버처럼 네트워크와 저장 성능이 중요한 환경에서 여전히 강한 존재감을 가진다.

<br>

### 3.3.3 솔라리스

솔라리스는 썬 마이크로시스템즈가 발전시킨 유닉스 계열 운영 체제로, 성능과 엔터프라이즈 기능 측면에서 큰 족적을 남겼다.<br>
SVR4 계열을 기반으로 하면서도 자체적으로 많은 성능 관련 기능을 발전시켰다.

<br>

특히 중요한 요소는 다음과 같다:
- VFS: 여러 파일 시스템을 하나의 추상 인터페이스 아래에서 다루게 해준다.
- 완전 선점형 커널: 실시간 성격의 작업에도 낮은 지연시간을 제공할 수 있다.
- 멀티프로세서 지원: SMP/AMP 지원을 강화해 다중 CPU 환경에 대응했다.
- 슬랩 할당자(slab allocator): 메모리 할당 성능을 크게 개선했고, 이후 다른 커널에도 영향을 줬다.
- DTrace: 프로덕션 시스템에서도 강력한 정적/동적 트레이싱을 가능하게 한 대표적인 관측가능성 도구다.
- Zones: 운영 체제 수준 가상화 기술로, 이후 컨테이너 개념과도 맞닿아 있다.
- ZFS: 높은 안정성과 기능성을 갖춘 파일 시스템으로, 오늘날에도 널리 언급된다.

<br>

즉, 솔라리스는 현대 운영 체제에서 당연하게 여기는 관측가능성, 파일 시스템 추상화, 가상화, 메모리 관리의 여러 개념을 한발 앞서 실용적으로 밀어붙인 계열이라고 볼 수 있다.

<br>
