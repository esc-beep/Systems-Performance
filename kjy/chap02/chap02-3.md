# CHAP 02-3 방법론 - 개념 

## 2.3.1 지연시간(Latency)
* 사례: HTTP GET 요청과 같은 네트워크 전송을 지연시간으로 나눠서 보여줌 
    * 네트워크 연결이 수립되기까지 기다리는 시간: 지연시간 
    * 지연시간+연산시간 = 응답시간(response time) 
* 지연시간: 어떤 연산이 수행되기 전에 기다려야하는 시간 
* 지연 시간을 측정 위치에 따라 다르게 나타날 수 있음 
* high level에서, 모든 지연 시간은 더 큰 지연시간의 일부로 간주될 수 있음

## 2.3.2 시간 스케일 
* CPU 사이클은 매우 작은 시간 스케일에서 동작

## 2.3.3 트레이드오프 
* CPU와 메모리 간의 관계 :
    * 메모리 캐시를 통해 CPU 사용감소 가능 
    * CPU 자원이 넉넉한 현대 시스템에서는 CPU 소비하여 데이터 압축함으로써 메모리 사용을 줄일 수 있음 
* 파일 시스템 레코드 크기(블록 크기) 
* 네트워크 버퍼 크기 

## 2.3.4 튜닝을 위한 노력 
* 성능 튜닝은 시스템엣어 작업이 이루어지는 가장 가까운 지점에서 수행하는 것이 가장 효과적 
    * 애플리케이션에서 부하가 일어난다면 애플리케이션에서 튜닝이 필요하다 
* 애플리케이션 분석 뿐만 아니라 운영체제 분석도 소홀히 하면 안됨

## 2.3.5 적합성의 수준 
* 성능 분석에 대한 투자 대비 효용(Return on Investment, ROI)이 조직마다 다를 수 있다 
    * 연간 수백만 달러를 컴퓨팅에 투자하는 환경에서라면 성능 전담팀 운영이 충분히 정당화됨
    * 컴퓨팅 예산이 비교적 적은 소규모 스타트업은 표면적인 성능 체크만 수행하고 서드파티 모니터링 솔루션에 의존해 성능을 확인/경고 받는 경우가 많음 => 그래도 성능 엔지니어링에 투자할 필요가 있다 (고객 만족도 향상을 위함)

## 2.3.6 분석을 언제 중단할 것인가 
성능 분석을 할때 언제 멈춰야 할지 결정하는 일이 어려움 
* 성능 문제의 주요 원인을 설명할 수 있을때 : 원인은 찾았으나 정확한 원인을 규명해야할 때는 더 들어가야함
* 잠재적 ROI가 분석 비용보다 작을 때: 성능 문제가 연간 수천만 달러로 추산되는 큰 성능 향상을 불러올 수 있을때 계속 들어가야함 
* 더 큰 ROI가 기대되는 다른 문제가 있을때: 위 2가지 시나리오가 해당되지 않더라도 더 큰 ROI가 기대되는 다른 문제가 우선순위가 될 수 있음 
-> 잠재적 ROI가 더 높은 작업이 우선순위가 될 것임 

## 2.3.7 성능 개선의 한시성 
환경의 성능 특성은 사용자 증가, 소프트웨어나 펌웨어 업데이트, 새 하드웨어 설치 등 시간에 따라 변할 수 있음 => 성능 튜닝 파라미터 값은 특정 시점에만 유효할 수 있음 
* 튜닝 파라미터 변경 시 버전 고나리 시스템에 변경 이력을 상세한 설명과 함께 저장하면 도움이 됨 
    * puppet, salt, chef와 가틍ㄴ 설정 관리 도구들 사용할 수 있음 

## 2.3.8 부하 vs. 아키텍처 
애플리케이션 성능이 저하되는 이유는 실행 중인 하드웨어, 소프트웨어 설정, 즉 아키텍처와 구현의 문제일 수 있음 
* 하지만 단순히 부하가 애플리케이션에 과도하게 걸리면서 큐가 길어지고 대기 시간이 늘어나는 경우에도 성능이 나빠질 수 있음 
* 성능 저하가 아키텍처의 문제일 수도 있음 
    * 멀티 스레드 환경을 사용해야하는 단일 스레드 환경을 사용한 경우 

## 2.3.9 규모 확장성 
* 규모 확장성(scalability): 시스템에 가해지는 부하가 증가할 때 성능이 어떻게 변화하는지 
* knee point: 두 가지 다른 성능 패턴 사이의 경계 지점
    * 일정 기간 동안은 선형적인 확장성을 보이다가 자원에 대해 경쟁이 시작되는 시점에서 스루풋이 감소하기 시작하는 시점 
    * 이는 시스템의 특정 구성 요소가 100% 사용률에 도달할 때 발생 -> 포화 지점 (saturation point)
        * 구성 요소가 더이상 추가작업을 처리할 여유가 없고 100%에 가까워질수록 queueing 이 자주 발생 -> 큐의 길이가 길어짐 
* 응답 시간 측면에서 선형 확장성을 유지하려면 애플리케이션이 작업을 큐에 추가하는 대신 자원이 부족할 때 오류를 반환하는 식으로 설계되어야함 

## 2.3.10 지표 
성능 지표(performance metrics)는 관심 대상을 측정하기 위해 시스템, 애플리케이션, 또는 추가 도구에서 선택한 통계 
* throughput, IOPS, utilization, latency 등 
* 오버헤드: 지표를 수집, 저장하기 위해서 CPU 사이클을 어느 정도 소비해야함 -> 오버헤드 발생하여 측정 대상 시스템의 성능에 부정적 영향 미칠 수 있음 => observer effect 
* 지표 문제: 개발사가 지표를 제시할 떄 버그 없이 정확하고 완전하게 투명성을 제공한다고 믿고 싶을 수 있으나, 실제로 각 지표는 혼동을 줄 수 있고 복잡하며 신뢰할 수 없거나 부정확할 수 있음 

## 2.3.11 사용률
사용률(Utilization)은 OS에서 CPU나 디스크와 같은 장치의 사용 상태를 나타내는데 자주 쓰이는 용어 <br>
사용률은 시간을 기준으로 하거나 수용량(capacity)을 기준으로 할 수 있음 
* 시간 기반 사용률: 서버나 자원이 특정 기간 동안 얼마나 많은 시간을 바쁘게 동작했는지를 측정하고 이를 전체 관찰 시간으로 나눈 비율 
    * U=B/T 
        * U= 사용률, T= 관찰 기간, B= T중 시스템이 동작 중인 총 시간 
    * 어떤 구성 요소가 얼마나 사용되는지를 잘 보여줌 
* 수용량 기반 사용률(capacity-based) 
    * 100% 사용률에 도달한 디스크는 더 이상 추가 작업을 처리할 수 없음을 의미 (그러나 시간 기반에서는 해당 구성 요소가 주어진 시간 동안 계속 바쁘게 동작했음을 의미)

## 2.3.12 포화도 
* 포화도(saturation): 자원에 요청되는 작업량이 처리할 수 있는 양을 초과하는 정도 
    * 사용률이 100%일 때(수용량 기준)부터 일어나게 됨 
    * 자원이 포화된 경우 추가 작업을 처리할 수 없게 되어 작업이 큐에 쌓이기 시작
* 포화도는 정도와 관계 없이 성능 문제로 이어질 수 있음 

## 2.3.13 프로파일링
프로파일링(profiling)은 대상 시스템의 활동을 기록하여 나중에 검토하고 이해할 수 있도록 함 
* 보통 일정 간격으로 시스템 상태를 샘플링하고, 나중에 해당 샘플들을 분석하는 형태로 이루어짐 
* 샘플링을 사용하면 대상 시스템의 활동을 대략적으로 관찰 가능 (얼마나 자세히? 는 샘플링의 간격에 따라)

## 2.3.14 캐싱 
캐시는 느린 저장 장치에서 가져온 결과를 더 빠른 저장 장치에 저장하여 참조 시간을 줄이는 방법 
* 대부분 메인 메모리를 저장 장치로 사용하는 소프트웨어 기반 캐시 
* hit ratio(히트율, 적중률): 필요한 데이터를 캐시에서 찾은 횟수(hit)와 전체 접근 횟수(Hit+miss)를 비교한 비율 
    * 높을수록 더 빠른 장치에서 데이터를 성공적으로 찾은 횟수가 많다는 의미 
* miss rate(시간당 미스 횟수): 미스가 발생할 때마다 성능에 미치는 영향과 비례 
* 실행 시간 = (초당 히트 횟수 x 히트 시 지연신간)+ (초당 미스 횟수 x 미스 지연시간)
<br>

* 알고리즘: 캐시 관리 알고리즘/정책은 제한된 캐시 공간에 어떤 데이터를 저장할지를 결정함 -> 캐시 유지 정책(retention policy), eviction policy(축출 정책)
    * MRU(Most recently used, 최근 사용 우선): 가장 최근에 사용된 데이터를 캐시에 우선적으로 남겨두는 방식 
    * LRU(least Recently Used, 최소 최근 사용): 캐시 축출 정책. 캐시에 빈 공간이 피룡할 떄 가장 오랫동안 사용되지 않은 데이터를 제거함 
    * MFU(most frequently used, 최대 사용 빈도), LFU(least frequentyl used, 최소 사용 빈도)
    * NFU(not frequently used, 적은 사용 빈도)
* 캐시의 상태 
    * cold: 캐시가 비어있거나 불필요한 데이터로 가득 찬 상태 
    * warm: 유용한 데이터가 들어있긴 하지만 히트율이 높지 않은 상태
    * hot: 자주 요청되는 데이터로 가득 차 있어서 히트율이 높은 상태
    * warmth: 캐시가 뜨겁거나 차가운 정도. 캐시의 온기를 늘리는 행동은 캐시 히트율을 높이려는 작업 의미 

## 2.3.15 모른다는 것을 아는 것들
* knowns-knowns (이미 알고 있는 것들)
* known-unknowns (모른다는 것을 아는 것들): 모른다는 사실을 인지하고 있는 것 
* unknown-unknowns (모른다는 것을 모르는 것들): 모른다는 사실조차 인지하지 못한 것들
