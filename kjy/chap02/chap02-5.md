# CHAP 02-5 방법론  
어디서부터 분석을 시작하고, 어떤 방법으로 진행할 것인가? 

## 2.5.1 가로등 반방법론 
Streetlight Anti-Method(가로등 반방법론)은 실제로는 특정 방법론이 없는 것을 의미 
* 인터넷에서 찾은 도구나 자신이 친숙한 도구를 사용하여 시스템 보면서 뭔가 눈에 띄는 일이 일어나고 있지 않나 살펴보는 것 
    * ex. top(1) 화면만 들여다보기 
* 익숙하다는 이유로 발생한 문제와는 관계가 없는 도구를 사용하거나 튜닝을 시도하게 되어 문제를 발견하는데 시간이 오래 걸리게 될 수 있음 
* 가로등 효과(streetlight effect)에서 유래 

## 2.5.2 임의 변경 반방법론 
임의 변경(random change)은 실험적인 반방법론. 사용자는 문제가 사라질 때까지 문제가 어디일지 임의로 추정하고 수정하는 과정을 반복함. 각 변경 후에는 성능 개선/오류 수정 여부를 확인하기 위해 결과 지표를 살펴봄(ex. 애플리케이션의 총 실행 시간, 연산에 걸리는 시간, 지연시간, 연산율, 스루풋 등을 확인함)
* 시간이 많이 소요되고, 최종적으로 얻는 튜닝이 장기적으로 의미가 없는 것일 수 있음 
* 언젠가는 테스트 부하에 대해 적용 가능한 튜닝 방법을 찾아낼 수는 있음 
* 더 심각한 문제의 원인을 제대로 이해하고 적용한 변경이 아닐 수 있어서 변경을 원래대로 돌릴 필요가 생길 수 있음

## 2.5.3 다른 사람 비난 반방법론 
1. 우리가 책임지지 않는 시스템이나 환경의 구성 요소를 찾음
2. 해당 구성 요소에 문제가 있다고 판단 
3. 문제를 해당 구성 요소를 담당하는 팀에게 넘김 
4. 만약 문제가 아닌 것으로 밝혀지면 1로 다시 감 
* 성능 문제를 검토하기보다는 다른 사람의 문제로 만들어버림 

## 2.5.4 전용 체크리스트 방법론 
미리 준비된 체크리스트에 따라 테스트하는 방식. 개발 지원 인력이 짧은 시간 안에 어떤 시스템을 검사하거나 튜닝해달라는 요청을 받을때 자주 사용됨 
* 체크리스트는 ad-hoc하게 작성됨, 비슷한 유형의 시스템에서 겪은 최근 경험과 문제를 바탕으로 작성됨 

## 2.5.5 문제 내역서 
문제 내역서(problem statement) 작성 -> 지원 부서 직원들이 문제를 처음 마주쳤을때 수행하는 기본적인 작업 
* 질문, 대답 과정에서 종종 문제 원인/해결책 빠르게 찾을 수 있음 

## 2.5.6 과학적 방법론 
가설 수립하고 이를 검증하여 연구하는 방법론 
* 질문(성능 문제 내역서) -> 가설 -> 예측 -> 테스트 -> 분석 

## 2.5.7 진단 사이클(diagnosis cycle) 
가설 -> 예측 -> 데이터 -> 가설
* 여기서는 수집된 데이터가 새로운 가설을 빠르게 도출할 수 있고, 그 다음 해당 가설을 검증하거나 다시 세밀하게 다듬음 

## 2.5.8 도구 방법론 
도구를 중심으로 함. 실행할 도구, 수집할 지표/지표를 어떻게 해석할지에 대한 체크리스트 만들 수 있음 -> 효율적이나 도구에 의존성 큼 

## 2.5.9 USE 방법론
* Utilization, Saturation, Error 를 분석. 성능 검토 초기 단계에서 시스템의 병목 지점을 분석하기 위해 사용함 
* 시스템 자원에 초점. 모든 자원에 대해 사용률, 포화도, 오류를 검사함 
* 오류 -> 포화도 -> 사용률 순으로 검토 
<br>

* functional block diagram: 자원을 나열하는 방법. 자원 간의 관계르 ㄹ보여주기 때문에 데이터의 흐름에서 나타날 수 있는 병목 지점 찾기 좋음 
* 마이크로서비스에서 분석 시 사용 가능 

## 2.5.10 RED 방법론 
마이크로서비스 아키텍처의 클라우드 서비스와 같은 서비스에 초점 맞춤. 사용자 관점에서 서비스 상태(health)를 모니터링하는 지표 확인 가능
* 요청률, 오류, 지속 시간 

## 2.5.11 워크로드 특성화(workload characterization)
가해진 부하로 인해 발생하는 문제를 식별. 시스템 성능의 결과보다 시스템에 가해진 입력(load)에 초점을 맞춤. 
* 누구? 왜? 무엇? 어떻게? 

## 2.5.12 드릴다운 분석
문제를 높은 수준에서 시작, 점차 초점을 좁혀가면서 흥미롭지 않은 부분을 제외하고 흥미로운 영역을 깊이 파고드는 방식 
* 모니터링 -> 식별 -> 분석 
* 추가 방법론: five whys? -> 스스로에게 왜?라고 묻고 그 질문에 답하는 과정을 총 5번(혹 그 이상) 반복하는 것

## 2.5.13 지연시간 분석 
어떤 연산이 완료되기까지 걸린 시간을 분석. 근본 원인 식별, 정량화할때까지 더 작은 구성 요소로 나눔. -> 지연시간이 가장 큰 더 작은 구성요소가 나올 때까지 계속 나눠서 각 부분이 얼마나 걸렸는지를 파악하는 작업 반복 

## 2.5.14 R 방법론 
오라클의 trace event를 기반으로 지연시간의 원인을 찾는 데 초점이 맞춰져 있음. 쿼리 처리 시 어느 부분에서 가장 많은 시간을 소모하는지 식별/수치화하는데 초점을 둠. 

## 2.5.15 이벤트 트레이싱 
시스템은 불연속적인 이벤트를 처리하면서 동작함. 개별 시스템을 트레이싱 하거나, 시스템 콜을 트레이싱 할 수 있음. 
* 입력, 시간, 결과 등의 정보 확인 가능 

## 2.5.16 기준 통계(baseline statistics)
시스템이 정상 부하 상태일때 모든 시스템 지표를 수집하여 나중에 참조할 수 있도록 기록해두는 것. 시스템/애플리케이션의 변경 전후, 일정한 간격으로 수집하여 성능 차이 분석하는데 사용 가능 

## 2.5.17 정적 성능 튜닝 
아키텍처 설정의 문제에 초점. 시스템이 유휴 상태일때(부하x) 수행 가능. 

## 2.5.18 캐시 튜닝 
애플리케이션/운영체제가 I/O 성능 향상을 위해 애플리케이션~디스크에 이르는 단계마다 캐시를 사용. 각 수준의 캐시를 튜닝하여 성능 향상 가능 (중복 캐싱 주의, 어느정도 성능 향상을 얻을 수 있을지 고려)

## 2.5.19 마이크로 벤치마킹
단순하고 인공적인 부하의 성능을 테스트. (실제 환경에서 자연스런 부하를 테스트하는 매크로 벤치마킹과 다름)
* 마이크로 벤치마킹은 다루는 요소가 적어 이해 쉽고, 수행 덜 복잡 
* load generator 사용해 워크로드 적용 가능 
* 추가적으로 고려할 요소들: 시스템 콜 시간, 파일 시스템 읽기, 네트워크 스루풋 

## 2.5.20 성능 최적화를 위한 지침(performance mantra)
성능을 최대한 향상시키기 위한 튜닝 방법론. 가장 효과적인 것부터 덜 효과적인 것 순서로 수행할 항목을 정리.
